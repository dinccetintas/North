# M4 — Growth, sales and the outcome ledger

Goal: a test campaign runs end to end on the user's own ad account; spend,
clicks and sign-ups land in the outcome ledger with provenance; the daily and
total caps are never exceeded silently (the 11th dollar pauses the campaign and
opens a card); first-contact emails go out only after one card per batch, from
the user's own mailbox; replies come back as a metric. Everything is provable
in sandbox from a cron and a smoke script; the live adapters sit behind the
founder's keys and the user's connections.

Requirements: OUT-1, OUT-2, DEC-1 (every new effect through the gate), DEC-3
(cap and batch cards count against the quota), ONB-3 (Meta Ads and Gmail are
connections), AGT-2 (message ids and campaign ids as evidence), kill switch
NFR. The spec's "Bütçe korumaları" bullets have no IDs; this plan labels them
**BUD-1** (per-category total and daily caps, enforced in code and in the
database), **BUD-2** (spend only from the user's own accounts; the platform
never custodies funds), **BUD-3** (a cap about to be exceeded stops the action
and opens a K2 card), **BUD-4** (the kill switch pauses active ads). The role
table's tier rows are **GRW-K2** (Growth: spending or publishing is a card) and
**SLS-K2** (Sales: first contact is a card; in-thread replies are K1). ADRs:
0009 (ledger data model and spend accounting), 0010 (growth and sales run on
user connections, never platform keys).

## Scope decisions (made here, revisit only with the founder)

- **Campaign = table, not payload.** `campaigns` is a mutable summary row per
  executed `ads.start` action (`action_id` unique). The audit stays in
  `actions` (every start/pause/resume is a row) and the numbers stay in
  `metrics` and `ledger_entries`; the table exists because the collector, the
  cap logic, the kill switch and the ledger page all need one stable key with
  a status. Owners read it; only the worker writes it.
- **Metric samples carry provenance and a scope.** `scope = 'company'` rows
  are the company's own series (what `latestMetric` and the goal bar read);
  `scope = 'channel'` rows are cumulative per campaign or batch with
  `provenance { provider, campaignId | batchId, messageIds, windowEnd,
  sandbox, raw }`. A company-level metric has exactly one source per mode
  (sandbox analytics in sandbox, PostHog/Stripe live), so channel attribution
  never double-counts the goal.
- **Attribution = one SQL function.** `record_attribution(...)` inserts the
  channel samples, the ledger entry (`before/after` = the campaign's or
  batch's cumulative attributed metric, `cost_usd` = spend in the window,
  `channel` = `meta_ads` / `cold_email`), applies the spend to `budgets`
  with the day roll, and returns `{ duplicate, cap_daily, cap_total }` in one
  transaction. A unique index on `(company_id, metric_key, provenance_key,
  window_end)` makes a retried step a no-op. This is BUD-1 "in the DB"; the
  gate is BUD-1 "in code".
- **The gate checks per-day and total separately** (fixes an M2 slip: a $50
  five-day campaign was compared to the $20 daily cap). `spendProfile(spec)` →
  `{ perDayUsd, totalUsd }`; `wouldExceedBudget` takes the profile.
- **Cap card.** When `record_attribution` reports `cap_daily` or `cap_total`,
  the worker first pauses the campaign (`ads.pause`, K1, through the gate,
  `notified`) and then opens one K2 card through the gate with the new kind
  `budget.cap.raise` (`spendsMoney` → K2; `amountUsd` = the raise, so a raise
  over $500 is K3 by the existing rule): "Today's ads cap ($10) is spent on
  *Acme launch test* ($11 so far). Raise today's cap by $10 and resume?"
  Options `approve` / `decline`, recommended `decline`, **default `decline`**
  (the campaign stays paused). Approve → `daily_extra_usd` for today only
  (total cap: `total_limit_usd` is raised) → `ads.resume` (K1) through the
  gate. A campaign paused for the daily cap resumes by itself when the day
  rolls (K1 `ads.resume`, reason `day_roll`: the original card approved that
  daily budget); a campaign paused for the total cap never resumes without a
  card. One cap card per campaign per day; while the quota is spent the
  campaign stays paused and the next hourly collection retries the card.
- **One card per outreach batch, one action per email.** Each
  `email.send.first_contact` stays its own action row (its own message id,
  its own evidence) but carries `payload.batchId`; the gate reuses the task's
  pending card for the same `batchId`, so five sends open one card ("Send 5
  first-contact emails?", facts list the recipients). Settlement performs
  every pending action of the card, each in its own step.
- **Ads and outreach credentials are user connections** (BUD-2, ADR 0010).
  `Integrations.ads` and `Integrations.outreach` become factories taking the
  user's `ProviderAuth`, like `code` and `deploy` in M3; the platform
  `META_ACCESS_TOKEN` / `META_AD_ACCOUNT_ID` env keys are removed. A missing
  `meta_ads` or `gmail` connection in live mode raises
  `ConnectionRequiredError` → connect card (the M3 mechanism). Platform
  Resend stays for decision notifications only.
- **Reply tracking.** `OutreachMailProvider.replies({ messageIds })` returns
  per-message reply counts. Sandbox: replies are simulated through a
  worker-only sandbox route and stored next to the sent message on disk.
  Live: Gmail `users.threads.get` per sent thread (messages after the send
  whose `From` is not the connected address). Both land in M4 because the
  Google OAuth and token refresh are needed for sending anyway; the thread
  read is one method on top. If the Google OAuth client is not ready when the
  live evidence run happens, the live read is recorded in M5 with the brief;
  the sandbox path proves the loop either way.
- **Scoped down to stub + interface:** Google Ads (`live/google-ads.ts`),
  PostHog (`live/posthog.ts`) and Stripe read (`live/stripe-read.ts`). The
  spec allows it: OUT-2 requires the *sources* and daily freshness, and the
  M4 acceptance names one test campaign; the `AdsProvider`,
  `AnalyticsProvider` and `PaymentsProvider` interfaces, their sandbox
  implementations and the collector are real, so each live adapter is one
  file later. Why each: Google Ads API needs a developer-token review that
  takes weeks and the spec puts Meta first; the landing page North ships
  carries no tracker (M3 build rule), so there is no PostHog data to read
  until the founder adds one; the user's Stripe OAuth (read) belongs with the
  Stripe work in M6 and no M4 company has paying customers yet.
- **Leads.** A `leads` table fed by a CSV upload (owner, ≤ 500 rows) and by a
  K0 `lead_research` task (sales) whose output `leads[]` the worker persists.
  `outreach_batch` receives the next unsent leads in its instructions.

## Flow (worker)

Growth, `run-task` for `campaign_spec`:

1. `executeTask` → one `ads.start` request (`amountUsd` = total, `payload`
   `dailyBudgetUsd`, `name`, `audience`, `targeting`, `creativeMarkdown`).
2. `gateAction`: `spendProfile` → per-day vs `dailyRemaining`, total vs
   `totalRemaining` → K2 card (`spends_money`, `public_statement`; no
   `budget_cap` unless a cap is really short). Task parks.
3. `settle-decision` on approve: `performPending` → `ads(auth).startCampaign`
   (sandbox: file under `<SANDBOX_ROOT>/ads/<campaignId>.json`; live: Meta
   campaign + ad set + creative + ad, `landingUrl` = the company's live or
   preview URL, status ACTIVE) → `completeAction` records `executed` and
   **registers the campaign row** (`registerCampaign`, idempotent by
   `action_id`). The task finishes with the campaign id as evidence
   (`evidenceKindFor("ads.start") = "campaign_id"`, verified by
   `ads.status(campaignId)`).
4. `collect-metrics` (cron `7 * * * *`) fans out `metric/collect
   { companyId, reason: "cron" }` to every company with a campaign in
   `active | paused_cap` or a first-contact send in the last 30 days, kill
   switch off. `collect-company-metrics` (concurrency 1 per company) runs:
   `pace` (sandbox + cron only: the adapter writes the hour's simulated
   delivery) → `ads-insights` per campaign → `attribute` (`recordAttributionWindow`:
   samples `ad_spend_usd`, `ad_impressions`, `ad_clicks` and the task's metric
   key, cumulative; ledger entry with the window's delta and spend) → `cap`
   (pause + cap card as above) → `day-roll` (campaigns `paused_cap` whose
   pause day is over and whose total cap is not reached → `ads.resume` K1) →
   `outreach-replies` → `analytics` and `payments` (company-scope samples).
5. Kill switch (`company/killswitch`): `pauseEverything` reads the company's
   `active` campaigns from the table and pauses each through the adapter
   concurrently (4 s timeout each; the SLA is 5 s), records one K1
   `ads.pause` row with the ids, marks rows `paused_kill`. This is the one
   path that records without `gate()`, as in M2: under an active kill switch
   the gate's only verdict is `block`, and the pause is the kill switch's own
   effect. `company/resume` re-dispatches tasks and, when campaigns are
   `paused_kill`, opens one K2 card `ads.resume` (`requestedTier: "K2"`,
   default decline): spend never resumes silently.

Sales, `run-task` for `lead_research` (K0) then `outreach_batch`:

1. `lead_research` → `lead_list` artifact + `output.leads[]` (≤ 50) persisted
   to `leads` (`source: research`, unique on email per company). CSV upload
   writes the same table (`source: upload`).
2. `outreach_batch` → `companyContext` passes the next unsent leads (≤ 5) as
   `vars.leads`; the fixture (and the guide for the SDK) emits one
   `email.send.first_contact` per lead with `payload.batchId`, `to`,
   `subject`, `text`, `leadId`.
3. `gateAction`: first action opens the card ("Send 5 first-contact emails
   to …?", `costUsd 0`, K2 `new_contact`); the other four reuse it
   (`existingBatchCard`) and record their own `pending` rows on the same
   `decision_card_id`.
4. `settle-decision` on approve: `pendingActionsForCard` → `perform-<i>` /
   `record-<i>` per action → `outreach(auth).send` → message id (sandbox:
   `sandbox:msg:<uuid>`, file under `<SANDBOX_ROOT>/mail/`) → leads marked
   `contacted`. Decline → every pending row `declined`. The task finishes with
   the first message id as evidence (`message_id`, verified through
   `outreach.status(messageId)`).
5. `collect-company-metrics` → `outreach-replies`: for each batch (executed
   first-contact heads grouped by `batchId`, last 30 days) →
   `outreach(auth).replies({ messageIds })` → channel sample `email_replies`
   (provenance `cold_email:<batchId>`) → ledger entry (`before/after`
   cumulative replies, `cost_usd 0`, channel `cold_email`) → leads with a
   reply marked `replied` → company sample `email_replies` (source
   `outreach`). A reply becomes a Signal/card in M5, not here.

## Decisions made while building

- **Cap-card idempotency is per campaign, day and cap level**, not per
  campaign and day: the acceptance's own step 3 needs a third card once the
  raised ($20) cap is breached. A declined or pending card for the same level
  opens nothing; a quota-deferred card is retried on the next collection and
  the deferred row is marked `retried`.
- **Cap check at perform time.** Approving a start or resume after the cap has
  since been spent fails the action with `budget cap: …` before the provider
  is touched (`services/budget-check.ts` mirrors the `campaigns_within_budget`
  trigger). The trigger is the backstop: a registration it refuses lands
  `paused_cap` with `last_error`, and the next collection re-pauses at the
  provider.
- **Smoke step 5 arithmetic.** The plan's count gives six cards for a quota of
  five. The second campaign starts under an `ads.start` auto rule (≤ $50) so
  the resume card is the fifth; the first campaign comes back through the day
  roll (pause day backdated, daily cap raised in settings as the CEO would),
  which also exercises `resumeAfterDayRoll` on the stack.
- **`support.reply.*` also goes through `outreach(auth)`** (ADR 0010: every
  outbound mail uses the user's connection; platform Resend only notifies the
  user).
- **Provenance discriminates on `channel`** (`meta_ads` / `google_ads` →
  `campaignId`; `cold_email` → `batchId` + `messageIds`), not on a `provider`
  field; `organic` has no provenance. The window's figures travel in
  `provenance.raw` so the ledger chips read `raw.clicks` without a second
  query.
- **`BudgetState.dailyExtraUsd` is required**, so no reader can silently
  ignore today's raise; `capExceeded` uses `>=` (at exactly the cap nothing
  more may be spent). `spendProfile` counts an ads spec without
  `dailyBudgetUsd` as spending the whole amount per day (conservative) and
  clamps per-day to ≤ total.
- **Owners write sandbox-scoped connection rows only** (migration 0007 from
  M3 applies to Meta and Gmail too); `leads` owner insert is limited to
  `source = 'upload'`, `status = 'new'`; `campaigns`, `metrics` and
  `ledger_entries` are owner select only; `budgets` owner writes are limited
  to the two limit columns.
- **`CampaignSpecSchema.landingUrl` is optional**: the sandbox accepts a
  missing URL (an onboarded company may have no site yet); live Meta refuses
  before any request. The worker fills it from `siteUrls` (live, else
  preview).
- **`pauseMany` returns `{ paused, failed }`** so the kill switch finishes
  even when one id fails; the sandbox reports ids of other companies as
  failed and never touches them.
- **`vars.leads` is a JSON string** (prompt vars are strings); `parseLeadsVar`
  is strict and the fixture falls back to its built-in five. The batch id is
  `batch-<taskId>` so a retried task reuses its card.
- **Outreach replies on the ledger page come from the ledger entries**, not
  from channel samples (one query instead of N+1).
