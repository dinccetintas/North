# M5 — Proactive layer

Goal: the user runs the company for seven days without opening a chat. Every
morning at 07:00 in the user's time zone a brief arrives (push + email, on the
home screen, readable in 60 seconds); the research agent scans its sources and
turns the one signal worth attention into a card with evidence links; an error
reported by Sentry becomes an engineering fix, a pull request and a preview
without anyone touching it, and only going live asks; on Monday the Chief of
Staff rewrites the plan from the outcome ledger and says, for every task type
it cut, why. Everything is provable in sandbox from the crons and a smoke
harness that advances the worker's clock through seven days; the daily quota
follows the user's clock, in code and in the database.

Requirements: BRF-1, PRO-1, PRO-2, PLN-2, DEC-3 (signal and fix cards count
against the quota; the quota day is the user's day: M2 review L2), DEC-1
(every new effect through the gate), AGT-2 (the fix is done with a verified
URL), EXP-1 (the fix PR lands in the user's repo). PRO-3 is V2; its cap exists
now and is labelled **PRO-3-CAP** (at most one "new opportunity" card per
company per week). The spec's observability NFR row is labelled **OBS-1**
(cost per task recorded and visible). ADRs: 0011 (time follows the owner's
zone; the worker clock is injectable), 0012 (signals become cards only
through the gate; weekly cap in the database; the brief is a table row),
0013 (the Sentry webhook lives in the worker; an error becomes a fix through
the M3 pipeline with a pull request).

## Scope decisions (made here, revisit only with the founder)

- **The quota day is the owner's local day, computed in the trigger.** Not a
  nightly rollover: a rollover cron makes "which day is this card on" depend
  on when the cron ran, and it would need one run per time zone. Instead
  `decision_cards` gains `opened_at timestamptz` (default `now()`; the worker
  sets it from its clock) and `assign_decision_card_seq` computes
  `new.day := (new.opened_at at time zone u.timezone)::date` from the same
  `users` join it already makes for the quota, before taking the advisory
  lock on `(company, day)`. The database stays the enforcement point: `seq ≤
  quota` per `(company_id, day)` is unchanged, the owner cannot insert cards,
  and the day is computed server-side from a timestamp, never trusted as a
  date. An unknown zone falls back to UTC in the trigger; a `users` trigger
  refuses to store a zone Postgres does not know, so the settings form fails
  loudly instead of silently resetting at UTC. Core gets `localDay(timezone,
  now)` so the web and the worker count "today" the same way
  (`cardsOpenedToday` now requires the day). **Budgets stay on the UTC day in
  M5**: `budget_apply`, `campaigns_within_budget` and the cap cards all key
  on `current_date`; moving them is a separate change with its own M4 tests
  (M6 follow-up, recorded in ADR 0011).
- **The worker has one clock.** `WorkerDeps.clock: () => Date`. Every
  time-dependent decision (brief hour, scan window, card `opened_at` and
  `dueAt`, overdue defaults, plan week, metric day) reads it. In production
  it is the wall clock. In sandbox mode on a loopback host the harness may
  set it through `POST /sandbox/clock { now }` (next to the M4 simulation
  routes, same mounting rule: 404 in live mode or off loopback). The crons
  (`daily-brief`, `scan-signals`, `plan-week-cron`) share their bodies with
  events (`brief/tick`, `signal/scan`, `plan/requested`) so the harness can
  run "this hour" now instead of waiting for it; both paths are idempotent
  (one brief per company-day, one signal per source reference, one plan per
  week). Days are not event-driven: a day is simply what the clock says.
- **The brief is a `briefs` row, not an artifact, and it is not written by a
  model.** One row per company and local day (`unique (company_id,
  brief_date)`, from 0001), `content` = core `Brief` JSON, rendered to
  markdown for the email and to the `BriefPanel` on the home screen.
  `composeBrief(input)` in core is deterministic: the numbers are the
  ledger's, the ordering is fixed (yesterday → metrics → decisions → today →
  spend → signals → escalations), and lists are trimmed by priority until
  the brief is under `BRIEF_MAX_WORDS = 200` (60 s at a slow reading pace).
  An artifact would need a storage upload and a version per day; a row is
  queryable ("was today's brief sent?") and cheap. The Chief of Staff still
  "writes" it in the product sense (the role owns the template and the
  brief is sent in its name); a model-written headline is M6 work once
  Langfuse traces exist to cost it. The brief is K0: it reads. Push and
  email go through the M2 notification channel (platform Resend / web-push,
  recorded in `notifications` with `kind: brief`), never through the gate,
  exactly as decision notifications do. The brief hour is fixed at 07:00
  local (`BRIEF_HOUR = 7`); a per-user hour is a settings field for M6.
- **A signal is a row; it becomes a card only through the gate.** `signals`
  gains `kind` (`opportunity | metric_drop | error`), `status` (`new |
  scored | below_threshold | card_opened | deferred | capped | approved |
  declined | converted`), `source_ref` (unique per company and source: a
  rescan never re-inserts a post), `title`, `url`, `excerpt`, `score`,
  `rationale`, `card_week`, `converted_card_id`, `converted_task_id`. Owners
  read; the worker writes. Conversion is the new action kind **`signal.pursue`**
  (risk profile: no external effect, K0 base) gated by the worker with
  `requestedTier: "K2"` and `origin: "worker"`, the same shape as the M4
  kill-switch resume card: the gate opens the card (reason `agent_raised`),
  it counts against the daily quota, a spent quota defers it (status
  `deferred`, retried by the next scan, never a second row), and the kind
  is in `WORKER_ONLY_KINDS`, so an agent run cannot request it. Approve
  performs the action: a `signal_research` task (research, K0) is created
  with the signal's facts as data and dispatched by settlement's follow-up;
  the external reference is `task:<id>`. Decline (the default) marks the
  signal `declined`. The card's question is `Look into "<title>"? (<source>,
  score 0.85)` and its facts carry the evidence URL, so the card "contains
  evidence links" (PRO-3) before PRO-3 ships.
- **Weekly cap in the database.** `PRO-3-CAP`: at most one `opportunity`
  card per company per ISO week of the owner's local day. Code checks first
  (`signalCardAllowed`), the database backs it: `signals.card_week` (`YYYY-Www`,
  set when the card opens) with a partial unique index on `(company_id,
  card_week) where kind = 'opportunity' and card_week is not null`. A unique
  violation becomes `SignalCapError` → status `capped` (the brief lists it as
  "held for next week"). `metric_drop` and `error` signals are not under the
  weekly cap (they are bounded by the daily quota and by dedupe); at most
  `SIGNAL_CARDS_PER_SCAN = 1` card opens per scan so one scan cannot empty
  the day's quota.
- **Scoring is one structured Haiku call, not an agent run.** The sources
  are read by the worker through `SignalSource` adapters (no model);
  candidates are scored in one `LlmClient.structured` call with the
  `classifier` alias (`packages/core/src/models.ts` resolves it; no model
  id anywhere else), output `{ scores: [{ id, score 0..1, summary,
  rationale }] }` validated with Zod; ids not in the batch are dropped,
  scores clamped. Tests and the mock worker use `MockLlm` (the ONB-1
  pattern), keyed `signal:score`, with a fixture record exported by
  `packages/agents`; on `LlmError` the heuristic scorer (source weight,
  thesis keyword overlap, recency) stands in so a scan never fails on the
  model. `metric_drop` signals are scored by rule (`0.75`), `error` signals
  are `1.0` and never scored. Threshold `SIGNAL_THRESHOLD = 0.7`.
  (The orchestrator's note said "MockRuntime in tests": the deterministic
  double here is `MockLlm`, because scoring is a single call; `MockRuntime`
  still runs the `signal_research` and `fix_error` tasks the signals open.)
- **Live signal sources: Reddit and competitor sites only.** Both are
  keyless public reads. Reddit: `https://www.reddit.com/search.json?q=…&sort=new&t=week`
  with a fixed User-Agent, 10 s timeout, 403/429 → "nothing this scan" with
  a warning (datacenter IPs are often refused; never a crash). Competitor
  sites: the URLs the competitor map recorded in memory, fetched under the
  verifier's host policy (no redirects, no private hosts, 256 KB cap, text
  only), title + first 400 chars + a content hash; a changed hash is a
  candidate, an unknown URL is a `baseline` candidate stored
  `below_threshold` without scoring. **Stub + interface** (`NotConfiguredError`
  with the reason): Product Hunt (its API is GraphQL behind a developer
  token: a key, which the founder enters later) and Google Trends (no
  official API; scraping the widget endpoint violates its terms). All four
  have sandbox implementations with deterministic fixtures keyed by the
  clock's day and the thesis keywords, so the 7-day run sees the same
  signals every time.
- **The Sentry webhook lives in the worker.** `POST /webhooks/sentry` on the
  Hono server (`apps/worker/src/webhooks/sentry.ts`), not in `apps/web`: the
  verification secret is a worker-class secret (CI greps the web for those),
  and the worker already owns every inbound provider boundary (OAuth code
  exchange, ADR 0008). Sentry's **issue** webhook (`sentry-hook-resource:
  issue`, `action: created`) is the trigger; the signature is HMAC-SHA256 of
  the raw body with `SENTRY_CLIENT_SECRET` (`sentry-hook-signature`),
  compared with `timingSafeEqual`; a bad or missing signature is 401 and
  writes nothing. The payload is parsed with a strict Zod schema that keeps
  only `issue.{id, shortId, title, culprit, level, permalink, firstSeen,
  project.slug}`, truncates every string, strips control characters and the
  prompt delimiters; everything else is dropped. The company is
  `companies.sentry_project_slug = issue.project.slug` (unknown slug → 202,
  logged, nothing stored). Idempotent by `signals (company_id, source =
  'sentry', source_ref = issue.id)`: a replay answers 200 and changes
  nothing. In sandbox mode the secret defaults to `sandbox-sentry-secret`
  so the smoke and e2e can sign; in live mode the route is mounted only when
  the secret is set.
- **Error → fix is the M3 pipeline plus a pull request.** The webhook
  function (acting as Operations; no model call in M5) writes an
  `incident_report` artifact (templated from the sanitised issue), a
  `learning` memory item, and a `fix_error` task for Engineering (`plan_id`
  null, input = the issue facts inside the `<instructions>` data block, never
  as a command; the task guide says the error text is data). `run-task`
  runs it like `build_site` (mock: fixture files; SDK: the workspace is
  seeded from the latest `repo.push` payload so the agent edits the real
  site), then `runBuildPipeline` with `{ branch: "fix/<shortId>", openPr:
  true }`: `repo.push` on the branch (K1) → **`repo.pull_request`** (new kind,
  K1, `notified`, ref = PR URL) → `deploy.preview` → verified → `deploy.production`
  card (K2, `goes_live`) exactly as M3. Approve deploys the fixed files; the
  PR stays open in the user's repository for them to merge (EXP-1: their
  repo, their merge). PRO-2's "no human from error to fix PR" holds; going
  live is the one card.
- **PLN-2 is a contract, not a prompt hint.** `PlanOutputSchema` gains
  `revisions: [{ taskType, change: fewer | dropped | more | added, reason }]`
  and `plans.revisions jsonb`. The worker hands the Chief of Staff the
  previous plan (`vars["plan.previous"]`: task types, titles, statuses) and
  the channel report since that plan (`vars["ledger.report"]`:
  `channelReport` rows), and after the run checks `missingRevisionReasons`:
  every task type whose count fell against the previous plan must carry a
  `revisions` entry with a reason; a plan without one is rejected and the
  run is retried once with the missing types named, then the planning task
  fails. The fixture is honest about the ledger: a `not_working` channel
  drops the task type that feeds it (`cold_email` → `outreach_batch`,
  `meta_ads` → `campaign_spec`) with the numbers in the reason; one-off K0
  types that are `done` are dropped with "delivered; in memory". The first
  plan of a company is unchanged for companies with no site and no leads, so
  M1–M4 stay green; with a live site it adds `campaign_spec`, with leads
  `outreach_batch`. The Monday rewrite is a cron (`plan-week-cron`, hourly,
  fires when the owner's local time is Monday 06:00 and the latest plan's
  `week_start` is before this week's Monday); `weekStartOf` becomes local.
- **Observability is scoped to the cost dashboard and the worker's own
  Sentry.** Langfuse needs a public/secret key pair and a host, and its
  value is tracing the SDK runtime's tool calls, which no sandbox run has.
  M5 ships `OBS-1` as: `/settings` → "Usage and cost" from `agent_runs`
  (per company, last 30 days: runs, tokens, cost, by role and task type, by
  day) and the worker initialising `@sentry/node` when `SENTRY_DSN` is set
  (no custom instrumentation). Langfuse and `@sentry/nextjs` move to M6
  with the first live-key evidence run. `agent_runs` becomes owner
  select-only (it was owner `for all` since 0001; a small hardening).
- **`metric_drop` is in scope but modest.** `detectMetricDrops(series)` in
  core compares the latest company-scope value of each outcome metric with
  its value seven days earlier (≥ 30 % drop, minimum base 10): a signal
  with `source: metrics`, scored by rule, converted like any other, listed in
  the brief. No model, no new table.
- **The Operations agent does not run a model in M5.** The webhook service
  is Operations the way the collector is Growth: deterministic, templated,
  recorded under `agent_role: ops_finance`. A templated incident report is
  better than a model's paraphrase of an error we must treat as data.

## Flow (worker)

Brief, every hour (`daily-brief`, cron `3 * * * *`, body shared with
`brief/tick`):

1. `briefTick(deps)`: `listActiveCompanies` (status `active`, onboarding
   `done`, with the owner's timezone; the kill switch does not exclude:
   a stopped company still gets its brief, which says so) → for each company
   where `localHour(tz, clock()) === BRIEF_HOUR` and `getBrief(companyId,
   localDay(tz, clock()))` is null → `brief/generate { companyId, day }`.
2. `generate-brief` (concurrency 1 per company, retries 2, **not** cancelled
   by the kill switch): `gather` (`briefInput`: ledger entries and executed/
   notified actions since the previous brief's `created_at` (else 24 h);
   latest company-scope value and the previous one per outcome metric; the
   active goal; pending cards and quota-deferred rows; today's plan tasks
   (latest plan, `queued | running | waiting_decision`); budgets; learning
   items titled `Escalated:` since the previous brief; signals since the
   previous brief; site URLs; kill switch) → `compose` (`composeBrief`, pure)
   → `store` (`createBrief`, idempotent: the unique key returns the existing
   row) → `notify-push` → `notify-email` (`notifyBrief`, `kind: brief`,
   subject "North: <company> morning brief <day>", body = `briefMarkdown`).
   Latency is measured from the event to the row (`< 60 s`).

Signals, every six hours (`scan-signals`, cron `17 */6 * * *`, fan-out
`signal/scan { companyId, reason: "cron" }` to active, onboarded, not-stopped
companies; `scan-company-signals` concurrency 1 per company, `cancelOn` kill
switch):

1. `context`: thesis, personas (where they gather), competitor URLs from
   memory → `signalQueries` (≤ 6 keywords) and `ScanInput { queries,
   communities, competitorUrls, knownRefs, since: clock() − 7 d }`.
2. `scan-<source>` per `integrations.signals` entry, each its own step: the
   adapter's candidates, or `[]` on `NotConfiguredError` / provider errors
   (logged, never fatal). Candidates are validated (`SignalCandidateSchema`)
   and inserted with `insertSignals` (status `new`; `on conflict (company_id,
   source, source_ref) do nothing`; `baseline` candidates land
   `below_threshold`).
3. `detect-drops`: `detectMetricDrops` over the last 14 days of company-scope
   samples → `metric_drop` rows (ref `metrics:<key>:<day>`, score 0.75).
4. `score`: the `new` rows (≤ 20) in one `scoreSignals` call → `scored`
   with `score`, `summary`, `rationale`; below `SIGNAL_THRESHOLD` →
   `below_threshold`.
5. `convert`: `deferred` rows first (oldest first: they already waited a
   day), then `scored` rows at or above the threshold by score, at most one
   card per scan: for `opportunity` check the weekly
   cap (`signalCardAllowed(signals, isoWeek(localDay))`; cap reached →
   `capped`); `gateStandalone(deps, signalPursueSpec(signal), existing)`
   with the company's pending `signal.pursue` rows as `existing` (a retry
   reuses the card) → `card` → `updateSignal { status: card_opened,
   converted_card_id, card_week }` (`SignalCapError` from the index →
   `capped`); `deferred` → status `deferred`; `blocked` → `declined` with
   the reason. `decision/opened` for every card.
6. `settle-decision` on approve: `performPending` → `performAction("signal.pursue")`
   → `createTask { role: research, taskType: signal_research, input:
   signalTaskInput(signal), metricKey: artifacts }` → `applyOutcome` marks
   the signal `approved` with `converted_task_id` → `followUp` sends
   `task/dispatch`. Decline → the pending row `declined` and the signal
   `declined` (`applyDeclined` in `outcomes.ts`). The research task finishes
   with its `signal_report` artifact as evidence (K0, no card).

Error → fix (`watch-errors` on `signal/detected` with `kind: error`;
`cancelOn` kill switch; the webhook itself only stores and emits):

1. Webhook: verify → parse → company by project slug → `insertSignals`
   (`source: sentry`, `source_ref: issue.id`, `kind: error`, score 1,
   status `new`) → inserted ? `signal/detected` : 200 "duplicate".
2. `watch-errors`: `incident` (artifact `incident_report` by `ops_finance`,
   learning memory item, signal → `converted`) → `fix-task` (`createTask {
   role: engineering, taskType: fix_error, input: fixTaskInput(issue) }`,
   signal `converted_task_id`; idempotent: an open `fix_error` task for the
   same `source_ref` is reused) → `task/dispatch`.
3. `run-task` for `fix_error`: `executeTask` seeds the workspace from the
   latest executed `repo.push` payload (`files`) when the fixture or the
   SDK returns none, runs the agent, then `runBuildPipeline(deps, step,
   taskId, files, { branch: "fix/<shortId>", openPr: true })`: `repo.create`
   (exists → `created: false`) → `repo.push` (branch) → `repo.pull_request`
   (K1 → `notified`, ref = PR URL; sandbox `sandbox://repos/<owner>/<name>/pull/<n>`)
   → `deploy.preview` → `verifyUrl` → `deploy.production` card. Settlement
   is the M3 path: approve → live URL evidence; decline → preview evidence.

Plan revision (`plan-week-cron`, cron `11 * * * *` → `plan/requested` for
companies whose owner-local time is Monday 06:00 and whose latest plan is
older than this week; `plan-week` unchanged otherwise):

1. `planContext`: previous plan (`latestPlan`), its task statuses, `channelReport`
   of the ledger entries since that plan's `created_at` (≤ 30 d), escalations,
   open signals → `vars["plan.previous"]`, `vars["ledger.report"]`,
   `vars["leads.count"]`, `vars["site.url"]`.
2. The run → `PlanOutputSchema` → `missingRevisionReasons(plan, previousTasks)`;
   non-empty → one retry with the types named in the instructions → still
   missing → `markTaskFailed`, `plan/failed` is not an event: the brief shows
   the failed planning task. Success → `createPlanWithTasks` with
   `revisions`, tasks dispatched as today.

## Shared contracts (core, first)

Owner: north-backend (`packages/core`). Everything below lands before the work
packages start; the other personas code against it.

- `time.ts` (new): `localDay(timezone, now) → YYYY-MM-DD`, `localHour`,
  `isoWeek(day) → YYYY-Www`, `weekStartLocal(timezone, now)` (Monday), all
  Intl-based and pure; `BRIEF_HOUR = 7`.
- `brief/types.ts` (new): `BriefSchema` (`day`, `companyName`, `stopped`,
  `yesterday: { outcomes: [{ what, metricKey, delta, costUsd, channel }],
  actions: [{ kind, status, description }] }`, `metrics: [{ key, value,
  previous, measuredAt }]`, `goal: { metricKey, target, current, dueDate } |
  null`, `decisions: { pending: [{ id, question, dueAt, tier }], deferred:
  number, answeredYesterday: number }`, `today: [{ taskId, title, role,
  status }]`, `spend: [{ category, spentTodayUsd, dailyCapUsd, spentTotalUsd,
  totalCapUsd }]`, `signals: [{ id, title, source, score, status }]`,
  `escalations: [{ title }]`, `wordCount`), `BRIEF_MAX_WORDS = 200`;
  `brief/compose.ts` (new): `composeBrief(input: BriefInput) → Brief`
  (deterministic; trims `today`, `signals`, `yesterday.actions`,

- `signals/types.ts` (new): `SIGNAL_KINDS`, `SIGNAL_STATUSES`,

  "competitor_sites", "metrics", "sentry"]`, `SignalCandidateSchema` (`source`,
  `sourceRef ≤ 200`, `title ≤ 200`, `excerpt ≤ 600`, `url` http(s) or null,

  ActionSpec` (kind `signal.pursue`, `agentRole: research`, `requestedTier:
  "K2"`, payload `{ signalId, kind, source, title, url, score, taskType:
  signal_research }`), `signalCardAllowed(signals, week)`, `signalTaskInput(signal)`
  (data-wrapped text for the research task); `authority/gate.ts`: `cardFacts`
  branch for `signal.pursue` ("source: reddit, score 0.85, evidence: <url>")

- `authority/action.ts`: `ACTION_KINDS` += `signal.pursue` (`flags({})`),
  `repo.pull_request` (`flags({ externalEffect: true })` → K1).
  `connections.ts`: `providerForAction("repo.pull_request") = "github"`,
  `signal.pursue` → null. `evidence.ts`: both → null.
- `incidents.ts` (new): `SentryIssueSchema` (strict; `id`, `shortId`,
  `title ≤ 200`, `culprit ≤ 200`, `level`, `permalink` https, `firstSeen`,
  `project: { slug }`; strings pass `sanitizeErrorText` = control chars and

- `events.ts`: `EVENT` += `briefTick: "brief/tick"`, `signalScan:
  "signal/scan"`; schemas `BriefGenerateSchema { companyId, day }`,

- `decisions/types.ts`: no change (the card draft is the gate's); `models.ts`:

- Tests `packages/core/test/m5.time-brief.test.ts` (local day at UTC+14 and

## Decisions made while building

Deviations from the text above, each with the reason. The plan's intent is
unchanged; these are the places where the contract met the code.

**Core**

- `sanitizeErrorText` strips delimiters and control bytes without inserting a
  space (`"<system>x</system>y"` → `"xy"`); the one test expectation that
  implied a space was corrected. Shared with `signals` and the brief through
  `packages/core/src/text.ts`.
- `BriefSchema` keeps metric keys and budget categories as `string` at the
  type level (runtime `refine` against the enums) so callers can build the
  input from plain arrays.
- `composeBrief` trims in the plan's order but in two passes (down to one
  item per list, then to zero) so the worst case keeps the capped signal
  visible; outcomes and actions render grouped and titles are cut to six
  words. Pending cards, outcomes, metrics and spend are never trimmed, so a
  pathological input (20 pending 200-character questions) can exceed 200
  words; the gatherer bounds the lists.
- `metricDropCandidate` names the real span ("in a week" / "in N days").

**Data**

- `listTasksByType` did not exist and was created (with `status?`).
- `actions.kind` has no CHECK constraint, so there was nothing to extend.
- `signals.source_ref` was added nullable, backfilled `legacy:<id>` and then
  set `not null`, so the migration is safe on a non-empty table.
- `updateSignal` stamps `scored_at` whenever `score` is patched.
- The trigger's UTC fallback for an unknown zone is unreachable through the
  schema (the `users` trigger refuses such zones); it stays as defence.
- `costSummary` takes an optional `timezone` for the by-day buckets.

**Runtime and integrations**

- `MockLlm` accepts function responders: the `signal:score` answer must name
  candidate ids that depend on the company's thesis, so a static record
  cannot script them. The responder reads the candidates back out of the
  prompt's data block and scores by pattern.
- `onboarding:clarify` is not in `MOCK_LLM_RESPONSES`: an unscripted key
  throws `LlmError` and `generateClarifyingQuestions` falls through to core's
  fallback questions, which is what the web already relies on.
- Sandbox pushes to `main` keep `.branches/` and `pulls/`, otherwise a later
  `build_site` push would erase the fix branch and the PR record.
- `live/competitor-sites.ts` denies every URL when no `allowUrl` is injected
  (with a warning at selection) instead of duplicating the worker's DNS-based
  host policy; the worker injects `hostIsPrivate` from its verifier.
- Reddit: any non-200 or malformed answer ends the scan with `[]`
  ("nothing this scan, never a crash"), not only 403/429/5xx.
- Revision reasons quote the report window ("cold_email: 5 sent, 0 replies
  in the week of 2026-10-12 ($0.00 spent); the channel is not working, so its
  task is cut") because the report covers "since the previous plan", not a
  fixed seven days.

**Web**

- `postSentryWebhook` returns `{ status, duplicate }` so the spec can assert
  the replay.
- `localDayFor` re-implements `localDay` inside `e2e/stack.ts`: Playwright
  does not transform workspace sources.
- Signals sit below the decision cards, not directly under the brief: the
  plan's "brief, cards, goal" order wins so ten signal rows never push the
  cards off the first 390 px screen.
- `decision-pr` renders `sandbox://` refs as a plain anchor without `target`
  (`data-sandbox="true"`); http(s) refs open in a new tab with
  `rel="noreferrer noopener"`; any other scheme is text. Reviewed in the
  security review below.

**Worker**

- `planWeek` is not idempotent per week on `plan/requested` (the cron body
  `planTick` is): the harness and M1–M4 send `plan/requested` right after
  onboarding, which must still produce a plan. `planWeek` returns `{ kind:
  "created" | "rejected" }`.
- `ledgerReport` synthesises the `cold_email` row from the action log and the
  `email_replies` metric when the ledger has none (the reply collector writes
  nothing for 0 replies); without it the "0 replies" revision could never be
  produced.
- `knownRefs` is read once per scan across all sources so the sandbox
  progression advances one step per scan (D1 reddit, D2 Product Hunt, …).
- `plan/tick` is a worker-local event literal; core's `EVENT` is unchanged.
- The ISO week is reserved on the signal row (`card_week`) before the card
  opens, so the index refuses a second opportunity card before any quota is
  consumed; deferred and blocked rows clear the reservation.
- Budget days follow the worker clock through `collectCompanyMetrics(now)`.

**Smoke harness**

- "A rescan inserts nothing" is proven on D5 (after the competitor change),
  not D3: the sandbox progression advances one step per scan.
- The D6 base sample is dated D6 − 7 d − 1 h: the sandbox analytics writes
  a `site_visitors` sample on every collect, which would otherwise win the
  base point.
- "6 cards, none open" is asserted for D1–D7; plan 2 legitimately opens an
  `ads.start` card for its own week on D8, and the harness asserts every D8
  card belongs to a plan-2 task.
- The D8 cron hour selection (`planTick`) is covered by the worker unit test;
  the harness sends `plan/requested` at Monday 06:00.
- A competitor URL is seeded in memory on D1 (no fixture records one) and a
  push subscription for the owner, so the brief's push row exists.
- Known gap carried from M2–M4: `auth.admin.deleteUser` at the end of a smoke
  returns 500 because the cascade hits the append-only trigger on `actions`;
  the M5 harness pauses the company instead of deleting, the older smokes
  still accumulate owners. Follow-up for M6.
