# M2 — Decision layer

Goal: no K2/K3 action runs without an answered card; the daily quota is never
exceeded; cards arrive by push and email; the kill switch stops everything in
5 s; every action is in the audit log. Must be complete before any agent
touches the outside world (M3, M4).

Requirements: DEC-1, DEC-2, DEC-3, kill switch, audit NFR.

## Flow (worker)

`run-task` after the agent run has persisted artifacts/memory:

1. For each requested `ActionSpec`: `gate()` with the real kill-switch flag,
   budgets and active auto rules.
2. `run` → execute through the integrations adapter (sandbox in M2) and record
   `executed` with `external_ref`; `notify` → record `notified` (brief in M5);
   `block` → record `blocked`.
3. `card` → `openCard` (DB trigger enforces quota; on quota breach the card is
   deferred: task stays `waiting_decision`, a `decision/deferred` note is logged
   and the morning cron re-tries), record action `pending` with
   `decision_card_id`, `markTaskWaiting`, send `decision/opened`, then
   `step.waitForEvent("decision/answered", { match: "data.cardId", timeout: dueAt })`.
   `null` (timeout) → `applyDefault` (K2 safe default; K3 has none → stays
   pending and is re-notified). Answer `approve` → execute via adapter → action
   `executed`; `decline` → action `declined`.
4. After all actions settle → `markTaskDone` with evidence (artifact id, or the
   adapter's external ref for action-only tasks) and ledger entry.

`decision/opened` → `notify-decision`: web push (web-push, VAPID from env;
sandbox records to `notifications`) + email (Resend adapter; sandbox records).
`company/killswitch` → `kill-switch`: `cancelOn` ends in-flight runs, the
adapter pauses active campaigns (sandbox: records), queued tasks are left queued
(dispatch refuses while the flag is on). `company/resume` → re-dispatch queued tasks.

## Shared contracts (core)

- `tasks/types.ts`: add task type `campaign_spec` (owner `growth`, artifact kind
  `campaign_spec`) whose fixture returns one `ads.start` action with `amountUsd`
  and `category: "ads"`, and `outreach_batch` (owner `sales`) returning
  `email.send.first_contact` actions. Both are K2 and exist so the decision
  layer can be exercised end to end with the mock runtime.
- `decisions/types.ts`: `CardAnswer = { cardId, optionId, answeredBy }` (exists
  as event schema); `applyDefault(card) → optionId | null`.
- `events.ts`: `decision/opened` payload `{ companyId, cardId, taskId }`,
  `decision/deferred`.

## Security review (north-security-reviewer, 2026-10-14) and fixes

Verdict before fixes: BLOCK (4 HIGH, 6 MEDIUM, 7 LOW). Every HIGH and MEDIUM
and most LOW items were fixed the same day and re-verified on the stack
(unit 35 worker tests, 119 integration tests, smoke M1/M2, Playwright M2).

| # | Finding | Fix |
| --- | --- | --- |
| H1 | `settleCard` executed on the `decision/answered` event's option, so a forged or replayed event ran a K2 action with the card still unanswered | Settlement moved out of the run into `settle-decision`: it reads the answer stored on the card and ignores the event payload beyond "wake up"; an unanswered card settles nothing |
| H2 | The gate checked `amountUsd` while the ads adapter spent `payload.dailyBudgetUsd` | `ActionSpecSchema` refuses a payload spend above `amountUsd`; the adapter spends `min(payload, amountUsd)`; the card rationale shows the payload facts ("$10/day, audience: …", "to …, subject: …") so approval is never blind (M9) |
| H3 | `markTaskWaiting` from `waiting_decision` threw on the deferred retry and on any task with two or more cards, orphaning cards and burning quota | Park the task only from `running`; a repeated gate of the same spec reuses the existing card and pending action; the fake db now runs the real state machine so the unit tests catch this |
| H4 | Perform and audit insert in one step: a retry re-executed the external call and the first run had no row | Record `pending` first, perform in its own durable step, record the outcome in a third (`gateAction` → `performPending` → `completeAction`) |
| M1 | `acceptAutoRuleAction` trusted client rule parameters | The server recomputes `suggestAutoRule` from the answered history; kind and category must match, the ceiling may not exceed the repeated approvals, the card must be approved, `maxAmountUsd` is required |
| M2 | Owners could insert `actions` rows and rewrite card fields | Migration 0006: owners read `actions` only; on `decision_cards` their only write is the three answer columns while unanswered (column grants + policy); tests prove both |
| M3 | Runs cancelled by the kill switch stranded answered cards; late K3 answers went nowhere | `settle-decision` on `decision/answered` (idempotent per card), `decision-deadlines` cron applies K2 defaults, `resume-company` re-emits answers for pending actions |
| M4 | Adapterless kinds became "executed" with a `sandbox:noop` reference used as evidence; `sandbox` came from the mode, not the adapter | Adapterless kinds are `blocked` (`no_adapter`); evidence never accepts `internal`/`noop` refs; the sandbox flag comes from the adapter result |
| M5 | A duplicate dispatch of a task waiting on a card marked it failed | `executeTask` returns `blocked` for a waiting task without deferred rows; `finishTaskIfIdle` leaves tasks with pending actions alone |
| L1 | Quota trigger race → unique violation instead of a quota error | Advisory lock per company and day in the trigger |
| L3 | Service worker opened any origin from the push payload | Same-origin check before `navigate`/`openWindow` |
| L4 | Raw database errors shown to the browser | Fixed messages; causes logged server-side |
| L5 | A lost `decision/answered` send was never retried | The second tap re-sends; the deadline cron is the fallback |
| L6 | Deferred scan filtered 1000 rows in JS | `payload @> {quota_deferred: true}` in SQL and an explicit superseded lookup |
| L7 | Push and email in one Inngest step | One step per channel |
| L2 | Quota day rolls at UTC midnight while settings promise the user's clock | Documented in settings copy; per-timezone day is M5 (brief) work |

Decisions made while implementing (ask if any should change):

- Push subscriptions and the VAPID key are optional; `/settings` hides the
  button when `NEXT_PUBLIC_VAPID_PUBLIC_KEY` is absent, and push/email in
  sandbox mode are recorded in `notifications` instead of sent.
- The decision email deep-links to `/c/<slug>/decisions/<cardId>`; the worker
  resolves the slug with `getCompanyById`.
- Card evidence shows the task and the latest artifacts of the requesting role;
  a direct action→artifact link is M3 work.
