# M6 — Subscription and launch

Goal: plans and credits are live in Stripe test mode, usage is visible, data and
code export work, the PWA installs, and the founder's own company runs for 30
days on the platform. A user subscribes, the entitlement decides how many
companies they may run and how much agent work the month includes, credits are
bought when they run out, agents stop the moment a subscription ends and the
data stays for 90 days with an export one click away; several companies read
as one portfolio brief; a company may show an opt-in public page; the legal
placeholders exist; and production (Vercel web, Fly worker, hosted Supabase,
Inngest Cloud) is described in files and checked by a read-only script.
Everything is provable in sandbox with a `StripeBilling` sandbox adapter, a
smoke harness and Playwright, as every M3–M5 integration was.

Requirements: BIL-1, BIL-2, EXP-1, MEM-2 (artifacts downloadable as MD, PDF,
PPTX), MULTI-1 (portfolio brief; no memory leakage between companies), DEC-1
(every new external effect through the gate), BRF-1 (per-user brief hour),
OBS-1 (Langfuse traces and web Sentry with the first live-key run), the M5
budget follow-up of ADR 0011 (budgets on the owner-local day). Unlabelled spec
rows are labelled here: **PWA-1** (mobile PWA: installable, offline brief),
**PUB-1** (public company page, opt-in, off by default), **LEG-1** (legal
placeholders: terms, privacy, acceptable use; counsel before launch), **OPS-1**
(production topology, secrets and the read-only production check), **RET-1**
(BIL-1's "data kept 90 days, exportable"). ADRs: 0014 (entitlements projected
from billing events; credits as a ledger; subscription end through the kill
switch), 0015 (production topology and where every secret lives), 0016 (data
leaves through exports and dies through the retention purge: the one delete
path).

## Scope decisions (made here, revisit only with the founder)

- **Stripe runs in test mode with keys the founder enters; sandbox is the
  default.** `Integrations.billing: BillingProvider` (`createCheckoutSession`,
  `createPortalSession`, `createCreditPackSession`, `cancelAtPeriodEnd`,
  `subscription`) has a `StripeBilling` live adapter (raw `fetch`, form-encoded
  bodies, `Idempotency-Key` = the session row id, recorded request shapes in
  tests) and a `SandboxBilling` adapter that simulates checkout, portal and
  webhooks deterministically. The sandbox checkout and portal URLs are pages
  on the worker (`/sandbox/billing/checkout/<id>`, `/sandbox/billing/portal/<customer>`),
  mounted under the M4 rule (sandbox mode, loopback host only, 404 otherwise);
  their buttons build Stripe-shaped events, sign them with
  `SANDBOX_STRIPE_WEBHOOK_SECRET = "whsec_sandbox"` and POST them to the
  worker's own `/webhooks/stripe`. The webhook path is therefore the only path
  that ever changes an entitlement, in sandbox and live alike. `pnpm smoke:m6`
  and Playwright run without a key.
- **The web never holds a Stripe key and never creates a session.** The
  settings page inserts a `billing_sessions` row (`kind: checkout | portal |
  credit_pack`, `status: requested`; the owner may insert only in that
  state) and sends `billing/session_requested`; the worker creates the
  provider session and writes `url` and `provider_ref` (service role; the
  owner cannot update). `/settings/billing/go/[sessionId]` polls the row under
  RLS for up to 20 s and redirects. The success redirect proves nothing: the
  page says "Confirming with Stripe" and polls `entitlements`, which only the
  webhook changes. This is the ADR 0008 shape (the web forwards, the worker
  holds the secret) and the CI grep gains `STRIPE_SECRET_KEY` and
  `STRIPE_WEBHOOK_SECRET`.
- **The Stripe webhook lives in the worker (ADR 0013 pattern).** `POST
  /webhooks/stripe` on the Hono server: `stripe-signature` (`t=<ts>,v1=<hex>`,
  HMAC-SHA256 of `<ts>.<raw body>` with the endpoint secret, `timingSafeEqual`,
  tolerance 300 s on the worker clock, `bodyLimit` 256 KB) → 401 on a bad or
  stale signature, nothing written. The body is parsed with a strict Zod
  union that keeps only the fields the projection reads from six event types
  (`checkout.session.completed`, `customer.subscription.created`,
  `customer.subscription.updated`, `customer.subscription.deleted`,
  `invoice.paid`, `invoice.payment_failed`); anything else is 200 "ignored".
  Idempotent by `billing_events.event_id` (unique): a replay is 200 `{
  duplicate: true }` and changes nothing. The user is resolved from
  `entitlements.stripe_customer_id`, with `client_reference_id` (a uuid that
  must be an existing user) accepted on `checkout.session.completed` only;
  an unknown customer is 202, logged, stored as an unapplied event. In
  sandbox mode on loopback the secret defaults to `whsec_sandbox`; in live
  mode the route is mounted only when `STRIPE_WEBHOOK_SECRET` is set.
- **Entitlements are rows the web reads and the worker enforces.** One
  `entitlements` row per user: `plan_id` (`solo | pro | scale`), `status`
  (`trialing | active | past_due | canceled | ended`), `company_limit`,
  `monthly_credits`, `price_usd`, `period_start`, `period_end`, `cancel_at`,
  `stripe_customer_id`, `stripe_subscription_id`, `ended_at`,
  `retention_until`, `purge_due`. The projection is pure core
  (`applyBillingEvent(entitlement, event, now)`), the worker persists it,
  owners select only, and `users.plan` is a mirror kept by a trigger. A new
  user gets a **14-day Solo trial** without a card (`trialEntitlement(now)`,
  inserted by `handle_new_auth_user`; every existing user is backfilled at
  migration time so M0–M5 specs and smokes keep creating their one company).
  Enforcement points, each tested: company creation (trigger
  `companies_within_entitlement`: active status and `count(status <>
  'archived') < company_limit`, advisory lock on the owner, else
  `check_violation` → `EntitlementError`; core `canCreateCompany` gives the
  web its message first), agent dispatch (`dispatchAllowed(deps, companyId)`
  at the top of `executeTask`, `scanCompanySignals`, `planWeek` and
  `openFixTask`: kill switch, entitlement, credits), and the end of a
  subscription (below). The brief, metric collection and exports keep
  running for an `ended` user until `retention_until`: they read.
- **"Agents stop when the subscription ends" is the kill switch.** On
  `customer.subscription.deleted`, on an unpaid `past_due` that Stripe closes,
  or when a trial's `period_end` passes with no subscription
  (`entitlements-tick`, hourly, body shared with `billing/tick`), the worker
  sets `status: ended`, `ended_at`, `retention_until = ended_at + 90 d`, and
  for every company of the owner `kill_switch_active = true` with
  `paused_reason = subscription_ended`, then emits `company/killswitch` per
  company: `cancelOn`, campaign pauses and the dispatch check do what M2–M4
  proved (5 s SLA, measured again here). `company/resume` is refused while the
  reason is `subscription_ended` and the entitlement is not active
  (`skipped: subscription_ended`); the web's kill-switch bar reads
  "Subscribe to resume" instead of offering resume. A new subscription
  (`customer.subscription.created` → `active`) clears the flag on every
  company paused for that reason and emits `company/resume`, which opens the
  M4 resume card for campaigns as it always did. The user's own kill switch
  sets `paused_reason = user` and is untouched by billing.
- **Credits are an append-only ledger; nothing decrements in place.**
  `credit_entries` (`kind: grant_plan | grant_pack | consume | expire |
  adjust`, signed `amount`, `ref` unique per user, append-only trigger).
  **One credit is one agent run** (any role, any runtime; mock runs count,
  so sandbox proves the machinery). Plan credits are granted on
  `invoice.paid` with `ref = plan:<subscriptionId>:<periodStart>` (a replayed
  invoice grants nothing twice); the trial grants Solo's credits once
  (`ref = trial:<userId>`); a pack is granted on a `mode: payment`
  `checkout.session.completed` with `ref = pack:<sessionId>`. Unused plan
  credits expire at the period roll (`expire` entry, `ref =
  expire:<periodStart>`); pack credits never expire. The worker writes one
  `consume` entry per `agent_runs` row (`ref = run:<agentRunId>`, after the
  run, in the same step that records the run). `dispatchAllowed` refuses a
  run at balance ≤ 0 (`blocked: credits_exhausted`; the task stays `queued`,
  the brief says so, one `usage_alert` notification per period); the database
  backs it with `credit_entries_no_overdraft` (advisory lock per user, a
  `consume` that would take the balance below `-CREDIT_GRACE = 5` is
  refused), so two concurrent runs cannot drain a user past the grace.
  Buying credits is the user's own click in Stripe: no card, no action kind;
  North never spends the user's money (BUD-2 unchanged). The spec's `usage`
  table becomes a projection (`usage_apply`, additive upsert, service role
  only, the `apply_budget_spend` pattern) the worker updates after every run:
  `credits_used`, `llm_cost_usd`, `sandbox_minutes` per owner-local month
  (`localMonth`). Model routing does not change (`models.ts` untouched).
- **Usage panel and the 40 % alert.** `/settings/billing` shows the period's
  inference cost (`agent_runs.cost_usd`) plus sandbox cost (`sandbox_minutes ×
  SANDBOX_USD_PER_MINUTE`, 0.01 by default; only the SDK runtime accrues
  minutes) against `price_usd`, as a ratio with the 40 % line
  (`USAGE_ALERT_RATIO = 0.4`, the spec's cost NFR). `usage-tick` (hourly,
  body shared with `usage/tick`) sends one `usage_alert` notification (push +
  email) per user per period when the ratio crosses the line
  (`usage.alerted_at`), and logs a warning the founder's Sentry sees. The
  per-task token cap and model routing already exist; this makes the number
  visible.
- **Export is a worker job to a private bucket; the web only requests and
  links.** The owner inserts an `exports` row (`kind: artifacts | data |
  full`, `company_id` or null for everything, `status: requested`) and the
  web sends `export/requested`; `build-export` (not cancelled by the kill
  switch, allowed while `ended` until `retention_until`) writes a zip to the
  private `exports` bucket at `users/<userId>/exports/<exportId>.zip`,
  records `manifest`, `bytes`, `status: ready`, `expires_at = +7 d`. Formats
  (MEM-2): every artifact as the exact markdown plus a PDF rendered by a
  pure-JS renderer (`pdf-lib`: headings, paragraphs, lists, code; no images,
  no browser in the worker image) and, for `investor_deck` and `plan`
  artifacts, a PPTX (`pptxgenjs`, one slide per H2). Data as JSON (one file
  per table the owner can read, the owner-visible columns only) and CSV
  (`ledger`, `actions`, `decision_cards`, `tasks`, `metrics`, `leads`). A
  `README.md` names the company's GitHub repository (the latest executed
  `repo.create` reference): the code is already theirs (EXP-1). Downloads are
  signed URLs (1 h) the web creates with the owner's client under a storage
  policy keyed on the second path segment (the artifacts pattern); the web
  process never streams the file. Export is K0 (it reads the user's own
  data; nothing leaves North), so it carries no action kind.
- **Retention and the purge (RET-1, ADR 0016).** `ended + 90 d` is
  `retention_until`. `retention-sweep` (daily, body shared with
  `retention/tick`) archives the companies of an `ended` user whose
  `retention_until` has passed (`status: archived`, `paused_reason:
  retention`) and sets `purge_due`. The purge is `purge_owner(user_id,
  reason)`: a `security definer` function executable by the service role
  only, which refuses unless the entitlement is `ended` and `retention_until
  <= now()`, disables the three append-only triggers inside its transaction,
  deletes the user's rows in dependency order, re-enables the triggers and
  writes a `purge_log` row (a hash of the user id, row counts, the reason).
  The worker deletes the user's storage objects first, calls the function,
  then `auth.admin.deleteUser` (nothing is left to cascade). **The purge is
  the one delete path in North** and it never runs on its own in M6:
  `RETENTION_PURGE_ENABLED` is off by default; the sweep only marks
  `purge_due` and the founder runs `scripts/purge-due.ts` (founder question
  below). The M2–M5 smoke owner cleanup is the same function: the harness
  ends the owner's entitlement, sets `retention_until` in the past (service
  role) and purges; the older smokes keep their pause convention until they
  are touched.
- **Portfolio is one screen, not a new email.** `/companies` becomes the
  portfolio: per company its status (running, stopped, paused for
  subscription, archived), pending cards, goal progress, and one
  **portfolio brief** composed deterministically in core
  (`composePortfolioBrief(briefs, day)`, ≤ `PORTFOLIO_MAX_WORDS = 300`, one
  section per company in a fixed order: headline, pending decisions,
  yesterday's outcomes, signals held) from today's `briefs` rows under RLS.
  It reads nothing else: no memory, no cross-company join, so MULTI-1's
  isolation is the RLS proof M0 already has plus a repository test that the
  portfolio query sees only the owner's rows. The per-company 07:00 push and
  email are unchanged; a combined email is a settings toggle for M7.
- **The brief hour is a per-user setting.** `users.brief_hour` (0–23,
  default `BRIEF_HOUR` 7); `briefTick` compares `localHour(tz, clock())`
  with the owner's hour. A settings field and a comparison, as ADR 0011 said.
- **Budgets move to the owner-local day (ADR 0011 follow-up).** The
  database gets `owner_local_date(company_id)` (the owner's zone, UTC
  fallback); `campaigns_within_budget`, `budget_apply`'s default day and
  `daily_extra_date` use it; the worker passes `localDay(tz, clock())` to
  `apply_budget_spend` and `raise_daily_cap`; the collector's day roll and
  the cap cards follow. M4 tests are re-run against an Istanbul owner at
  23:30 and 00:30 local. The brief's spend section stops saying "UTC day".
- **The public page renders owner-chosen content, every string as text.**
  `public_pages` (one row per company: `headline` ≤ 120, `blurb` ≤ 600,
  `show_goal`, `metric_keys` ⊆ outcome keys, `show_site_link`) is written by
  the owner; `companies.public_page_enabled` (from 0001, owner-updatable
  since 0011) is the switch, off by default. Anonymous readers never touch a
  table: `public_page_view(slug)` is a `security definer` function granted to
  `anon` that returns the chosen fields only when the switch is on (else
  null → 404). `/p/[slug]` lives outside the `(app)` group, is cached 60 s,
  uses no markdown component and no `dangerouslySetInnerHTML`; `noindex`
  until the owner also ticks "listed". Nothing on it links to the app.
- **PWA: manifest, service worker, install prompt, the latest brief
  offline.** `app/manifest.ts` serves `/manifest.webmanifest` (name, short
  name, `start_url: /companies`, `display: standalone`, theme and
  background, 192/512 and maskable icons under `public/icons/`). `sw.js`
  keeps the M2 push handlers and gains a fetch handler: `_next/static/*`
  cache-first (immutable), navigations network-first with `/offline` as the
  fallback. **The offline cache holds the latest brief only**: the
  `BriefPanel` writes the brief JSON it rendered into Cache Storage
  (`north-brief-v1`, key `/brief/<slug>`); `/offline` is a static page that
  reads it client-side and renders the brief sections with `data-offline`
  and the day. Nothing else is cached (cards must never be answered from a
  stale copy). The install prompt is a dismissible bar on `/companies`
  (`beforeinstallprompt` on Chromium; a "Share → Add to Home Screen" hint
  on iOS Safari), dismissal remembered in `localStorage`. Lighthouse 12
  removed the PWA category, so the evidence is Lighthouse 11
  (`scripts/lighthouse-pwa.sh` runs `lighthouse@11 --only-categories=pwa`
  against the dev server and keeps the report under `docs/evidence/M6/`)
  plus a Playwright check that the manifest validates and the worker
  controls the page.
- **Legal placeholders are markdown files with a draft banner.**
  `apps/web/content/legal/{terms,privacy,acceptable-use}.md` rendered by
  the existing `Markdown` component (our own content) at `/legal/[doc]`, each
  with "Draft: counsel review before launch" and the placeholders
  `[operating entity]`, `[jurisdiction]`, `[contact address]`. Footer links
  on the landing page, login, settings and the public page; Stripe Checkout
  is configured with `consent_collection.terms_of_service: required` once the
  terms URL is set in the dashboard (runbook step).
- **Production is files plus docs, verified read-only.** Vercel hosts the
  web (`apps/web/vercel.json`, root directory and env list in
  `docs/runbooks/production.md`), Fly the worker (`apps/worker/fly.toml`
  gains the full secrets list as comments and a second `[[vm]]` note for
  the SDK runtime), hosted Supabase (`supabase link` + `supabase db push`,
  the two private buckets, auth providers, SMTP), Inngest Cloud (two app
  syncs: web `/api/inngest` and worker `/api/inngest`, one event key, one
  signing key), Stripe (`scripts/stripe-setup.ts` creates the products and
  prices from `packages/core/src/billing/plans.ts` with lookup keys and
  registers the webhook; idempotent), Sentry (two projects), Resend, VAPID.
  `scripts/production-check.ts` reads the live deployment and changes
  nothing: web and worker health lines (mode, runtime, webhooks mounted,
  clock = wall), anonymous Supabase `select` on `companies` returns zero
  rows, both buckets private, the manifest and the service worker served
  with the right content types, the Inngest introspection endpoint reports
  the function count, the Stripe webhook endpoint exists and is enabled
  (read with a restricted read-only key the founder passes in the shell),
  every user's usage ratio. Production stays `INTEGRATIONS_MODE=sandbox`,
  `AGENT_RUNTIME=mock` until the founder flips the two secrets (CLAUDE.md
  #5), and the check prints which mode it found.
- **Observability with the first live-key run (OBS-1).** The worker
  initialises Langfuse when `LANGFUSE_PUBLIC_KEY`, `LANGFUSE_SECRET_KEY` and
  `LANGFUSE_HOST` are set: one trace per agent run (`agent_runs.trace_id`),
  spans for the SDK's tool calls from the `PreToolUse` hook, cost from the
  result; no prompt text is sent when `LANGFUSE_REDACT=1` (default). The web
  gets `@sentry/nextjs` with `NEXT_PUBLIC_SENTRY_DSN` (a public DSN; the CI
  grep is tightened to `(^|[^_])SENTRY_DSN` so it keeps forbidding the
  worker's). Both stay off without keys; the smoke proves nothing about them,
  the founder's run does.
- **Prices and credits are configuration.** `packages/core/src/billing/plans.ts`
  is the source of truth: `SUBSCRIPTION_PLANS` (Solo $99 / 1 company / 300
  credits, Pro $299 / 3 / 1 000, Scale $999 / 10 / 4 000), `CREDIT_PACKS`
  (`pack_100`: 100 credits, $29), `TRIAL_DAYS = 14`, `RETENTION_DAYS = 90`.
  Stripe prices carry lookup keys (`north_solo_monthly`, `north_pack_100`);
  the worker resolves a price by lookup key at checkout; changing a number
  means editing the file and re-running `stripe-setup` (which creates the new
  price and transfers the lookup key). The founder may change every number
  (questions at the end).
- **The user's own Stripe read (OUT-2) ships, small.** The M4 stub said it
  belonged with the Stripe work: `stripe` joins `OAUTH_CODE_PROVIDERS`
  (Stripe Connect OAuth, `read_only` scope, the ADR 0010 shape) and
  `live/stripe-read.ts` reads active subscriptions and paid charges of the
  connected account into `paying_customers`, `mrr_usd` and `revenue_usd`
  samples. The founder's company needs it for a 30-day run with a revenue
  goal; without a connection the collector sees `ConnectionRequiredError` as
  before.

## Flow (worker)

Checkout and portal (`billing/session_requested`, `create-billing-session`,
concurrency 1 per session, retries 2):

1. `load`: `getBillingSession(sessionId)` (`requested`, else done) → the
   owner's entitlement (customer id, or none).
2. `customer`: no `stripe_customer_id` → `billing.ensureCustomer({ userId,
   email })` → stored on the entitlement (idempotent: `metadata.north_user_id`
   lookup first).
3. `session`: by kind → `createCheckoutSession({ customerId, lookupKey,
   mode: subscription, clientReferenceId: userId, successUrl, cancelUrl })`,
   `createPortalSession({ customerId, returnUrl })` or
   `createCreditPackSession({ customerId, lookupKey, mode: payment })` →
   `setBillingSessionReady(sessionId, { url, providerRef })`; a provider error
   → `failed` with a fixed message, the page shows it.

Webhook → entitlement (`POST /webhooks/stripe` stores and emits;
`apply-billing-event` on `billing/event`, concurrency 1 per user, retries 3):

1. Route: verify → parse (strict) → resolve user → `insertBillingEvent`
   (`event_id` unique; duplicate → 200 `{ duplicate: true }`) → `billing/event
   { billingEventId, userId }` → 200.
2. `project`: `getEntitlement(userId)` → `applyBillingEvent(entitlement,
   event, clock())` (pure) → `upsertEntitlement` → `markBillingEventApplied`.
3. `credits`: `creditGrantsFor(event, entitlement)` → `insertCreditEntries`
   (conflict on `ref` ignored) → the period roll's `expire` entry when
   `period_start` moved.
4. `effects`: status became `ended` → `endSubscription(deps, userId)` (kill
   switch + reason on every company, `company/killswitch` each); status became
   `active` from `ended | trialing-expired` → `reactivate(deps, userId)`
   (clears `subscription_ended` flags, `company/resume` each); `past_due` →
   one `billing_past_due` notification. Every effect is idempotent on the
   company's current flag and reason.

Ticks: `entitlements-tick` (hourly `23 * * * *`, `billing/tick`): trials past
`period_end` with no subscription → `ended` → `endSubscription`. `usage-tick`
(hourly `41 * * * *`, `usage/tick`): `usageAlertDue` per user → `usage_alert`
notification, `usage.alerted_at`. `retention-sweep` (daily `07 4 * * *`,
`retention/tick`): `ended` with `retention_until < clock()` → archive
companies, `purge_due`; with `RETENTION_PURGE_ENABLED=1` also
`purgeOwner(deps, userId, "retention")`; expired exports' objects removed.

Dispatch (every run): `executeTask` → `dispatchAllowed(deps, companyId)`
(`getKillSwitch` → `getEntitlementForCompany` → `creditBalance`) → `blocked`
with `kill_switch | subscription_ended | retention | credits_exhausted` (the
task stays `queued`; `blocked` is already a `run-task` outcome) → the run →
in the step that records `agent_runs`: `insertCreditEntries([{ kind: consume,
amount: -1, ref: run:<id> }])` and `usage_apply(userId, localMonth, 1,
costUsd, sandboxMinutes)`. The portfolio and company screens show "paused:
credits" from the latest blocked reason on the task.

Export (`export/requested`, `build-export`, concurrency 1 per user, retries
1, not cancelled by the kill switch):

1. `load`: the `exports` row (`requested` → `running`), the owner's companies
   (one or all; `archived` excluded unless the owner asked for it).
2. `artifacts`: per company, per artifact row (every version):
   `getArtifactMarkdown` → `artifacts/<company-slug>/<kind>/<slug>-v<n>.md`,
   `.pdf` (`renderPdf`), `.pptx` for deck and plan kinds (`renderPptx`).
3. `data`: per company, `data/<company-slug>/<table>.json` for every
   owner-readable table and the five CSVs; `data/profile.json` (profile,
   entitlement, credit entries, usage) once.
4. `bundle`: `README.md` (what is inside, the repo URL per company, the
   export date) → zip (streamed, `archiver`) → `exports` bucket →
   `setExportReady(exportId, { storagePath, bytes, manifest, expiresAt })`;
   any error → `failed` with a fixed message. The web lists rows and signs
   the URL on click.

Portfolio (web only): `listBriefsForDay(db, localDay(profile.timezone,
now))` under RLS → `composePortfolioBrief` → `PortfolioBrief` panel. No
worker step; the rows exist because `generate-brief` wrote them.

## Shared contracts (core, first)

Owner: north-backend (`packages/core`). Everything below lands before the work
packages start; the other personas code against it.

- `billing/plans.ts` (new): `SUBSCRIPTION_PLAN_IDS = ["solo", "pro", "scale"]`,

## Decisions made while building

Deviations from the text above, each with the reason. The plan's intent is
unchanged; these are the places where the contract met the code. Changes
made by the security fixes are listed in the review table below, not here.

**Core**

- The Stripe schemas read the real list shapes (`items.data[0].price.lookup_key`,
  `lines.data[].period`) and accept both API shapes (the 2025-03 "basil"
  `items.data[0].current_period_*` and `invoice.parent.subscription_details`).
  The plan's `items[0]` / `lines[0]` shorthand would have rejected every real
  event.
- "Strict" means strip-to-whitelist (the Sentry pattern), not `.strict()`:
  real Stripe bodies carry dozens of keys North never reads.
- The Inngest payload for `billing/event` is `BillingEventPayloadSchema`;
  `BillingEventSchema` is the Stripe event (the CONTEXT term). Both are
  exported, so they cannot share a name.
- An older event (by `created`) never changes status, period, cancel/end
  dates or `purgeDue`, but still fills plan fields and Stripe ids: Stripe
  does not order `subscription.created` against `invoice.paid`, and ignoring
  the older one could leave a paying user on the trial's plan.
- The trial's `priceUsd` is 0 (no card, so no usage ratio and no alert); its
  grant is `grant_plan` with ref `trial:<userId>`.
- `expireEntry` takes `{ periodStart, balance, planGrant }` because the
  worker holds the balance; plan credits are spent first, so the unused part
  is `min(balance, planGrant)`.
- `dispatchDecision` takes the company's `pausedReason`, so a pause set by
  billing reports `subscription_ended` / `retention` rather than
  `kill_switch`. The order (switch, entitlement, credits) holds.
- The portfolio's `held` line counts `capped` signals and is the last thing
  trimmed before pending cards, which are never trimmed.
- The brief gained a `usage` line (ratio, cost, plan price) after the first
  smoke run: phase 4 needs the brief to name the month's usage, and
  `BriefSchema` had no field for it. Stored M5 briefs still parse
  (`.default(null)`).

**Data**

- Three migrations (`0012_m6`, `0013_m6_pages_exports_purge`,
  `0014_m6_budget_day`) and four `schemaM6*` test files instead of one each,
  for the 400-line rule.
- The budget functions keep their object input with `day` required, not the
  plan's positional arguments, so existing callers keep compiling.
- `listActiveCompanies` includes `paused` companies (archived ones stay
  out): a company paused by billing still gets its brief (phase 6). The plan
  tick and the signal scans already skip companies with the kill switch on.
- `purge_owner` disables five triggers, not six: `purge_log`'s own trigger
  stays on because the function only inserts into it.
- `entitlements.last_event_created` added (core's `Entitlement` needs it);
  the trial values are written in SQL and in core, and a schema test compares
  the two.
- Hardening beyond the plan: owners cannot write `users.plan` or `email`;
  owners insert companies with only `owner_id`, `name`, `slug`; insert column
  grants on `billing_sessions` and `exports`; the `companies_pause_state`
  trigger (no lifting a `subscription_ended` / `retention` pause, no
  archiving by the owner); the company-limit trigger refuses another user's
  `owner_id` before its message could reveal that user's plan;
  `billing_events` accepts only the handled types and is append-only except a
  one-time `applied_at`.
- The public page's SQL returns raw facts; the repository renders them
  through core's `publicPageView`. An archived company has no public page.
- A6-6's test wording conflicted with smoke phase 5; phase 5 wins: at 00:30
  Istanbul the next spend starts a new day.
- Test cleanup goes through the purge: every user now holds an append-only
  trial credit row, so a plain `auth.admin.deleteUser` can no longer cascade.
  `deleteTestUser` ends the entitlement, removes the storage objects, calls
  `purge_owner('test')` and deletes the auth user. This closes the M2–M5 gap
  of smoke owners accumulating.

**Runtime and integrations**

- With no connection, the live Stripe read throws `NotConfiguredError`, like
  the other live adapters; `ConnectionRequiredError` stays worker-only.
- `cancelAtPeriodEnd` is sandbox-only (cancelling in live is the user's own
  click in the portal); the sandbox simulations return full Stripe-shaped
  events because the worker signs and posts the raw body.
- Every session result carries `providerRef` (portal ones as `bps_…`);
  `subscription()` reads `GET /v1/subscriptions?customer=…&status=all&limit=1`.
- Return URLs: https, or http on a loopback host; credentials refused; the
  string passes to Stripe unchanged so `{CHECKOUT_SESSION_ID}` survives.
- No `Stripe-Version` header is pinned in the adapter (a wrong string would
  fail every call); the parsers accept both shapes and `stripe-setup.ts` pins
  the webhook's `api_version`.
- The user's Stripe read adds `revenueUsd` (trailing 30 days, net of partial
  refunds, USD only); each list stops at 1 000 objects or 10 pages.
- A second sandbox checkout replaces the customer's subscription; the web
  sends active subscribers to the portal to switch plans, never to a second
  checkout.

**Web**

- M6 e2e helpers live in `e2e/stack-m6.ts` (`stack.ts` would pass 400 lines).
- The billing spec checks that grants total 1 300 and that the displayed
  balance equals the ledger sum: the onboarding runs consume credits, so an
  exact "1300" is not stable.
- The checkout success URL is `/settings/billing?checkout=<billingSessionId>`
  on the web's own origin, so the session cookie is present on return.
- `task-blocked` comes from the live `dispatchDecision`; there is no stored
  per-task block reason.
- No resume button while billing-paused; the toggle action refuses a resume.
- Service worker: `_next/static` is cache-first only for responses marked
  `immutable` (production); dev chunks go network-first with the cache as
  fallback. `/sw.js` is served `no-cache`. The push and notification
  handlers are byte-identical to M2.
- Browser Sentry loads through Next 16's `src/instrumentation-client.ts`
  only when the DSN is set; both configs use `sendDefaultPii: false` and a
  scrubber.
- "The portfolio page never reads memory" is proven by a unit test on the
  loader's imports; the local PostgREST logs only errors, so the e2e check is
  best-effort.
- The home's artifacts strip pins an incident report from the last 7 days
  (at most two) ahead of the six newest artifacts (`lib/artifact-strip.ts`).
  M5 promised "the strip shows the incident report", and with the weekly
  plan's documents finishing right after it, recency alone pushed it out.
- `repo.create` is a notify-tier action recorded as `notified`, so the export
  page lists repository references from `notified` or `executed` actions.
- The offline brief moved to a production-build spec,
  `e2e/m6-offline.prod.spec.ts`, run by `pnpm e2e:prod`
  (`playwright.prod.config.ts`, port 3200). The dev server's client waits
  for its hot-reload socket before hydrating, so no dev page renders
  offline; and `context.setOffline` does not cover the service worker's own
  fetches unless service-worker routing is on
  (`PW_EXPERIMENTAL_SERVICE_WORKER_NETWORK_EVENTS=1`), which the spec then
  aborts with `context.route`. The install-bar step dispatches the stand-in
  `beforeinstallprompt` until the hydrated listener has taken it.

**Worker**

- The customer-to-user lookup is a direct, Zod-checked select in
  `services/billing-lookup.ts`; `@north/db` had none.
- When `invoice.paid` arrives before `subscription.created`, the credits step
  reads the plan from the provider's current subscription.
- A zero-credits alert was added (phase 3 asks for one per month); it is
  tracked through the notification log, not `alerted_at`, so the 40 % alert
  keeps its own month.
- `resumeAllowed` refuses whenever the entitlement is not active, not only
  for `subscription_ended`; `endSubscription` sends a kill-switch event for
  every non-archived company, including ones the user had paused.
- `openFixTask` checks the signal's company before asking dispatch; a refusal
  leaves the signal `deferred` for retry-deferred.
- The data export reads through a paged reader with explicit owner-visible
  column lists (`services/export/tables.ts`, checked against the generated
  types): the table repositories return recent rows only, so an export
  through them would be incomplete.
- The pinned fetch is wired into the competitor source only:
  `SelectOptions.fetchImpl` is shared with Stripe and Reddit, and Reddit
  needs redirects. `isPrivateAddress` now also catches IPv4-mapped,
  IPv4-compatible and NAT64 IPv6 forms (`[::ffff:127.0.0.1]` was missed by
  the M3 verifier).
- Six CSVs, not five (`EXPORT_CSV_TABLES` has six). A PDF or PPTX that fails
  to render (or markdown over 5 MB) is left out and named in the README; the
  `.md` is always kept.
- `purge.test.ts` (integration) skips without the stack unless
  `REQUIRE_INTEGRATION=1`.

**Smoke harness and scripts**

- The run has 11 billing events, not 9: Pro checkout 3, pack 1, cancel 1,
  end 1, Solo checkout 3, period advance 1, second end 1. The advance proves
  the period roll (plan grant under the new ref, expiry under the old).
- The M5 and M6 smokes cannot run at the same time: both move the shared
  worker clock.
- `scripts/lighthouse-pwa.sh` runs Lighthouse 11 against the dev server; the
  PWA category scored 100.

Deviations from the reviewer's proposed fixes:

- M3: the rule is "the plan line's price is above 0", not `amount_paid > 0`:
  a renewal paid from the customer's balance or offset by a downgrade's
  proration credit is legitimately $0 and must still grant.
- M1: an invoice for a subscription the entitlement does not follow still
  earns its own period's credits (money was received) but never moves or
  expires the followed period. "Delete is terminal" is approximated: an ended
  entitlement comes back through the same subscription only on a strictly
  newer event, because Stripe can revive `unpaid` / `paused`.
- L9 is stricter than asked: dispatch refuses at 0, so the −5 grace now
  covers only consumes written after the fact.
- M4: the rate limit binds signed-in owners; the worker never inserts exports.
- L3: the gate refuses only when the entitlement exists and has ended; an
  unknown company is already refused by the kill switch, which fails closed.
- L6: Stripe's hosts stay allowed in sandbox mode, because the runbook keeps
  the web in `sandbox` while the worker goes live.
- L15: `apps/web/e2e` is excluded from the grep (the Playwright helpers seed
  the stack with the service role; they never ship).
