# North: domain glossary

Canonical names for the concepts in `docs/SPEC.md`. Code, database and UI use the
English `Code name`. Turkish names are the spec's wording.

| Term | Code name | Definition |
| --- | --- | --- |
| Company (Şirket) | `Company` | One venture the user runs. A user may own several. Every other record belongs to exactly one company. |
| Thesis (Tez) | `Thesis` | One-paragraph idea, target customer and why-now. Versioned. The root of every agent's context. |
| Goal (Hedef) | `Goal` | A measurable target: metric key, target value, due date. At most three active per company. |
| Budget (Bütçe) | `Budget` | Money the user authorises agents to spend, per category (ads, tools, domain, other), with a total and a daily cap. Spent from the user's own accounts. Spent amounts are written only by the worker through `apply_budget_spend`; today's cap may be raised for the day by a cap card (`dailyExtraUsd`, reset at the day roll). A cap counts as reached once spend equals it. |
| Campaign (Kampanya) | `Campaign` | One ads campaign North started on the user's ad account: a mutable summary row per executed `ads.start` action (provider, provider campaign id, name, daily and total budget, landing URL, spent and delivery totals) with a status in `active`, `paused_cap`, `paused_kill`, `paused_user`, `ended`. Owners read it; only the worker writes it. |
| Cap Card (Limit kartı) | `CapCard` | The K2 card (`budget.cap.raise`) opened after a campaign was paused for a reached daily or total cap: "Raise today's cap by $X and resume?". Options `approve` / `decline`, recommendation and default `decline`. One per campaign per day; a raise over $500 is K3. |
| Lead (Aday müşteri) | `Lead` | One prospect a sales task may contact: name, email, company, why; `source` `upload` (CSV, ≤ 500 rows) or `research` (a K0 `lead_research` task); status `new`, `contacted`, `replied`, `bounced`, `opted_out`. Unique per company by email. |
| Outreach Batch (Erişim partisi) | `OutreachBatch` | The first-contact emails of one `outreach_batch` task, sent from the user's own mailbox: one `email.send.first_contact` action per lead sharing one `batchId`, gated by exactly one decision card. Identified by `batchId`; replies come back as the `email_replies` metric. |
| Agent (Ajan) | `Agent` | An AI employee with one role, a fixed tool list and a maximum action tier. Roles are defined in `agents/*.yaml`. |
| Chief of Staff | `ChiefOfStaff` | The agent role that turns goals into plans, dispatches tasks, measures outcomes, writes cards and the brief. Roles never hand work to each other directly; every handoff passes through it. |
| Plan | `Plan` | Chief of Staff's weekly work plan for a goal: tasks with expected metric impact and cost. Rewritten on the owner's Monday from the outcome ledger; every task type whose count fell against the previous plan carries a `PlanRevision` with a reason, or the plan is rejected. Not the subscription: that is `SubscriptionPlan`. |
| Subscription Plan (Abonelik planı) | `SubscriptionPlan` | One of `solo`, `pro`, `scale` (BIL-1): a monthly price, a company limit (1 / 3 / 10) and a monthly credit allowance, defined once in `packages/core/src/billing/plans.ts` with a Stripe lookup key; `scripts/stripe-setup.ts` creates the Stripe objects from the file. Column `plan_id`. The spec's `Plan` (weekly) keeps its name. |
| Entitlement (Yetki) | `Entitlement` | One `entitlements` row per user: `plan_id`, `status` (`trialing`, `active`, `past_due`, `canceled` = ends at the period end but still active, `ended`), `company_limit`, `monthly_credits`, `price_usd`, the period, `cancel_at`, the Stripe customer and subscription ids, `ended_at`, `retention_until`, `purge_due`. Projected by the worker from `BillingEvent`s through the pure `applyBillingEvent`, which follows one subscription (another subscription's invoices and updates change nothing; a delete of the followed one ends it, late or not; an `incomplete` one changes nothing) and is reconciled against Stripe by `entitlements-tick` 3 days past `cancel_at` / `period_end`; owners read; `users.plan` mirrors `plan_id`. Enforced by the `companies_within_entitlement` trigger (creation) and `dispatchAllowed` (every agent run). |
| Trial (Deneme) | `Trial` | The `trialing` `Entitlement` every new user gets for `TRIAL_DAYS` 14 with Solo's limits and credits, no card; inserted by the auth trigger. A trial that passes its `period_end` with no subscription is `ended` like a cancelled one. |
| Billing Event (Fatura olayı) | `BillingEvent` | One Stripe webhook event the worker accepted at `POST /webhooks/stripe` (signature and timestamp verified, strict schema, seven types), stored append-only in `billing_events` keyed by the Stripe event id (a replay is a duplicate) before it is applied, as the reduced parsed event plus `payload_sha256` of the raw body; rows no user owns are swept after 30 days. A checkout's user hint counts only for a `BillingSession` the worker created. The only thing that changes an `Entitlement`, in sandbox (the `SandboxBilling` pages post the same shape) and live. |
| Billing Session (Ödeme oturumu) | `BillingSession` | A `billing_sessions` row the owner inserts as `requested` (`kind` `checkout`, `portal` or `credit_pack`); the worker, which alone holds the Stripe key, creates the provider session and writes the `url` (`ready`) or a fixed error (`failed`); the web polls and redirects. A second subscription checkout is refused while one is open (`completed_at`, 35 minutes). The success redirect proves nothing: only the `BillingEvent` does. |
| Plan Revision (Plan değişikliği) | `PlanRevision` | One entry in `plans.revisions`: `taskType`, `change` (`fewer`, `dropped`, `more`, `added`) and a `reason` (1-500 chars) naming the ledger numbers behind it. `missingRevisionReasons(plan, previousTasks)` lists the shrunk task types without one; a non-empty list rejects the plan (one retry, then the planning task fails). |
| Task (Görev) | `Task` | One unit of work for one agent: input, output, status (`queued`, `running`, `waiting_decision`, `done`, `failed`), cost, metric key, attempts. `done` requires evidence. |
| Evidence (Kanıt) | `Evidence` | A verifiable reference that proves a task finished: URL, deploy ID, sent-message ID, test result. |
| Action (Eylem) | `Action` | One step that touches the outside world (send email, start campaign, deploy). Always classified into a tier and written to the audit log. Append-only: a status change (`pending` → `executed`/`declined`) is a new row that `supersedes` the previous one; the latest row of a chain is the action's state. |
| Tier (Katman) | `Tier` | Risk class of an action, assigned by the rule engine, never by the agent: `K0` automatic, `K1` notify, `K2` decision card, `K3` user only. An agent may raise a tier, never lower it. |
| Decision Card (Karar Kartı) | `DecisionCard` | A single decision for the user: question, 2-3 options, recommendation, safe default, due time. The only way a K2 action runs. |
| Decision Quota (Günlük kota) | `DecisionQuota` | Maximum cards per user per owner-local day (default 3, range 1-5). Never exceeded. The day is computed by the database from the card's `opened_at` in the owner's zone (`LocalDay`), never trusted as a date; a spent quota defers a signal card instead of refusing it. |
| Auto Rule (Otomatik onay kuralı) | `AutoRule` | A user-accepted standing answer ("auto-approve ad tests under $50") created after the same decision is made three times the same way. |
| Signal (Sinyal) | `Signal` | A `signals` row the proactive layer captured from a `SignalSource`: `kind` `opportunity` (trend, competitor move), `metric_drop` or `error`; `source_ref` unique per company and source (a rescan never re-inserts); `title`, `url`, `excerpt`, `score` 0..1, `rationale`. Status `new` → `scored` → `below_threshold` or (score ≥ `SIGNAL_THRESHOLD` 0.7) `card_opened`, `deferred` (quota spent; retried next scan), `capped` (see Opportunity Cap); answered `approved` (a `signal_research` task) or `declined`; `error` signals go `converted` into a `FixTask`, or stay `below_threshold` (a level under `error`) or `deferred` (the day's fix-task cap; the hourly `retry-deferred` re-emits them on a later `LocalDay`, M6). It becomes a card only through the gate, as the worker-only K2 action `signal.pursue`; owners read, the worker writes. |
| Signal Source (Sinyal kaynağı) | `SignalSource` | One adapter the worker reads without a model: `reddit`, `producthunt`, `google_trends`, `competitor_sites` (`Integrations.signals`), plus the internal `metrics` (drop detection) and `sentry` (the webhook). `scan(input)` returns candidates; a source that is not configured or fails contributes nothing to that scan, never an error. Every source has a deterministic sandbox fixture. |
| Opportunity Cap (Fırsat sınırı) | `OpportunityCap` | PRO-3-CAP: at most one `opportunity` card per company per ISO week of the owner's local day. Checked in code (`signalCardAllowed`) and enforced by the partial unique index on `signals (company_id, card_week)`; the refused signal is `capped` ("held for next week"). `metric_drop` and `error` signals are not under it. At most one signal card opens per scan. |
| Outcome Ledger (Sonuç Defteri) | `OutcomeLedger` | Append-only record of what each task/action changed in which metric, at what cost. |
| Metric | `Metric` | A time series per company (`metric_key`, value, source, measured_at, scope). `company` scope is the company's own series (goal bar, brief), with exactly one source per mode; `channel` scope is what one campaign or batch contributed (see Metric Sample). Sources: Stripe, analytics, ad APIs, email replies. |
| Metric Sample (Metrik örneği) | `MetricSample` | One row of a metric. Scope `company`: the company's value at `measured_at`. Scope `channel`: the cumulative value attributed to one source, with `Provenance` discriminated on `channel` (`meta_ads` / `google_ads` with `campaignId`; `cold_email` with `batchId` and `messageIds`; plus `windowEnd`, `sandbox`, `raw`) and a `provenanceKey` (`meta_ads:<campaignId>`, `cold_email:<batchId>`). Written only by the worker. |
| Channel (Kanal) | `Channel` | Where a metric change came from: `meta_ads`, `google_ads`, `cold_email`, `organic`. The ledger's `channel` column and the channel report use it; `organic` carries no provenance. |
| Attribution Window (Atıf penceresi) | `AttributionWindow` | One collection interval for one source, closed at `windowEnd`. Two cumulative samples give the ledger entry (`windowDelta`: `before`, `after`, `costUsd` = spend in the window, never negative). The unique key (`company`, `metric_key`, `provenance_key`, `window_end`) makes a replayed window a no-op. |
| Company Memory (Şirket Hafızası) | `Memory` | Thesis, personas, decisions, documents, learnings and the founder's preferences (`memory_items`, kinds in `MEMORY_KINDS`), searchable by words and by meaning: LRN-7 embeds each item inside Supabase (gte-small, 384 dimensions, a pgmq queue and the `embed` Edge Function) and `search_memory_hybrid` fuses the two ranks. An item is `active` or `retired` and may expire (`valid_until`); only active, unexpired items are searched or listed. All agents read the same memory. |
| Artifact (Artefakt) | `Artifact` | A persistent output produced by an agent (PRD, business plan, deck, website, creative). Versioned and downloadable. |
| Brief (Brifing) | `Brief` | Morning summary per company: one `briefs` row per company and `LocalDay` (`unique (company_id, brief_date)`), composed deterministically from the ledger at 07:00 local (`BRIEF_HOUR`), not written by a model. Sections in fixed order: yesterday, metrics, decisions, today, spend, signals, escalations; trimmed to `BRIEF_MAX_WORDS` 200 (60 seconds), pending cards never trimmed. K0: it reads. Delivered as push and email through the notification channel (`kind: brief`), never through the gate; shown in the `BriefPanel` on the home screen and kept as the one offline copy in the PWA. A stopped company still gets one that says so; a company paused for billing or out of credits gets a `blocked` line after the headline. The hour is the owner's `BriefHour`. |
| Brief Hour (Brifing saati) | `BriefHour` | `users.brief_hour` (0–23, default `BRIEF_HOUR` 7): the owner-local hour `briefTick` compares against. A settings field and a `localHour` comparison, not a new cron (ADR 0011). |
| Portfolio Brief (Portföy brifingi) | `PortfolioBrief` | MULTI-1: the one screen (`/companies`) across an owner's companies, composed deterministically in core (`composePortfolioBrief`, ≤ `PORTFOLIO_MAX_WORDS` 300) from today's `briefs` rows under RLS and nothing else: per company the headline, pending cards, yesterday's outcomes, held signals, in a fixed order (companies with pending cards first). It is not a new email and never reads memory, so cross-company isolation is the RLS proof. |
| Kill Switch | `KillSwitch` | "Stop all agents": freezes the queue, pauses every campaign that may still deliver (`active`, and a cap or user pause the provider may not have applied) within 5 seconds, and takes no card answer until resume. Present on every screen. Set by the user (`PausedReason` `user`) or by billing when a subscription ends (`subscription_ended`); while the owner's entitlement is `ended` no pause is lifted, whatever its reason (the `companies_pause_state` trigger, every caller), and the gate and `performPending` refuse every action but `ads.pause`. |
| Paused Reason (Durma nedeni) | `PausedReason` | `companies.paused_reason`: `user` (the kill switch button), `subscription_ended` (the `Entitlement` ended; cleared by a new subscription, which emits `company/resume`), `retention` (archived by the retention sweep). The kill-switch bar and the portfolio read it; billing never touches a `user` pause. |
| Connection (Bağlantı) | `Connection` | A user's OAuth link to an external tool (GitHub, Vercel, Stripe, Gmail, Meta Ads). Tokens encrypted at rest and read by the worker only (ADR 0008); in sandbox mode "Connect (sandbox)" records one without a token. |
| Connect Card (Bağlantı kartı) | `ConnectCard` | A K2 card with options `connected` / `skip` opened when a task needs an account the user has not connected (ONB-3). It carries no action: "connected" re-dispatches the task, "skip" (the default) marks it failed. |
| Incident (Olay) | `Incident` / `IncidentReport` | One error Sentry reported about the user's product, received by the worker's `POST /webhooks/sentry` (HMAC-verified, strict schema, company by `sentry_project_slug`), stored as an `error` `Signal` keyed by the issue id (the issue in `payload`, written with the row). The `IncidentReport` is the `incident_report` artifact templated from the sanitised issue by Operations (no model). The error text is data everywhere, never an instruction. The company's `sentry_project_slug` is a claim the worker alone writes (`scripts/set-sentry-project.ts`, founder only) until a Sentry connection proves it (M7). |
| Fix Task (Düzeltme görevi) | `FixTask` | The `fix_error` Engineering task an `Incident` opens (one per issue, `fatal` or `error` level only, at most `FIX_TASKS_PER_DAY` 3 per company per `LocalDay`; `plan_id` null; input = the issue facts inside the data block). Runs like `build_site`, then the M3 build pipeline on branch `fix/<shortId>` with a `PullRequest`, a verified preview and one `deploy.production` card. `done` only with verified URL evidence. |
| Pull Request (Çekme isteği) | `PullRequest` | The K1 action `repo.pull_request` the fix pipeline performs after `repo.push` on the fix branch: `notified`, external reference = the PR URL (`sandbox://repos/<owner>/<name>/pull/<n>` in sandbox), through the user's GitHub connection. The PR stays open in the user's repository; the user merges. |
| Data Block (Veri bloğu) | `dataBlock` | How untrusted text (an error title, a post, a page) enters a task input or a prompt: `<data source="…" id="<nonce>">` … `End of data` `</data id="<nonce>">`, the nonce random per call (`dataBlockNonce`), every line inside passed through `sanitizeText`, which strips prompt delimiters (the `data` tag included) and a sentinel line. The guides say the block is data, never instructions. |
| Local Day (Yerel gün) | `LocalDay` | `YYYY-MM-DD` of a timestamp in the owner's time zone (`localDay(timezone, now)` in core; `(opened_at at time zone u.timezone)::date` in the database, UTC fallback for an unknown zone). The unit of the decision quota, the brief, the week (`isoWeek`, `weekStartLocal`), the usage month (`localMonth`) and, since M6, budgets: `owner_local_date(company_id)` in the database, `localDay(tz, clock())` passed by the worker to `apply_budget_spend` and `raise_daily_cap` (the ADR 0011 follow-up). |
| Worker Clock (Çalışan saati) | `WorkerClock` | `WorkerDeps.clock: () => Date`, the worker's single source of time for every time-dependent decision (brief hour, scan window, card `opened_at` / `dueAt`, overdue defaults, plan week, metric day). Wall clock in production; in sandbox on loopback the harness sets it through `POST /sandbox/clock`. Cron bodies are shared with events so "this hour" can be run on demand. |
| Credit (Kredi) | `Credit` | One agent run (any role, any runtime; mock runs count). The balance is the sum of `credit_entries`, an append-only ledger per user: `grant_plan` (on `invoice.paid` with `billing_reason` `subscription_create` or `subscription_cycle`, the period from the subscription's own line, `ref plan:<subscription>:<periodStart>`, once per period), `grant_pack` (`pack:<session>`, only once paid at the pack's exact price), the trial's grant, `consume` (`run:<agentRunId>`, −1, reserved at dispatch by `credit_reserve`, which refuses at a balance of 0; `release:<agentRunId>` gives it back when the run never started), `expire` (unused plan credits at the period roll; pack credits never expire), `adjust` (a manual row with a note). Nothing decrements in place. `dispatchAllowed` refuses a run at balance ≤ 0 (`credits_exhausted`; the task stays queued, the brief says so); the trigger `credit_entries_no_overdraft` refuses a `consume` below `-CREDIT_GRACE` 5. |
| Credit Pack (Kredi paketi) | `CreditPack` | A one-off purchase of credits (`CREDIT_PACKS` in `plans.ts`: `pack_100`, 100 credits, $29) through a `payment`-mode checkout; granted by its `BillingEvent`. The user's own click in Stripe: no action kind, no card; North never spends the user's money. |
| Usage (Kullanım) | `Usage` | The spec's `usage` table as a projection per user and owner-local month: `credits_used`, `llm_cost_usd`, `sandbox_minutes`, `alerted_at`, written only through `usage_apply` (service role) after every run. The usage panel shows inference plus sandbox cost (`SANDBOX_USD_PER_MINUTE`) against the plan price; `USAGE_ALERT_RATIO` 0.4 sends one `usage_alert` notification per period. |
| Export (Dışa aktarma) | `Export` | EXP-1 / MEM-2: an `exports` row the owner requests (`artifacts`, `data` or `full`; one company or all) and the worker's `build-export` job fulfils: a zip in the private `exports` bucket at `users/<userId>/exports/<id>.zip` with every artifact as exact markdown plus a PDF (and a PPTX for decks and plans), JSON per table and CSVs, and a README naming each company's GitHub repository. Downloaded through a 1 h signed URL the owner's client creates; expires after 7 days. K0, no action kind; allowed while `ended` until `retention_until`; never built by the web process. One being built per owner at a time and `EXPORT_DAILY_CAP` 5 requests per 24 hours (`exports_rate_limit`, `ExportRefusedError`); rows stream to disk page by page, free-text columns are cut at `EXPORT_TEXT_MAX_CHARS` 20 000 in the select, and an `ExportBudget` (16 MiB per table, 45 MiB per export, under the 50 MiB upload limit) bounds the zip; the README names every cut. |
| Public Page (Herkese açık sayfa) | `PublicPage` | PUB-1: `/p/[slug]`, off by default (`companies.public_page_enabled`), showing only what the owner chose in `public_pages` (headline, blurb, the goal, up to three metric keys, the site link, `listed` for indexing). Anonymous readers get it through `public_page_view(slug)` (security definer; null unless enabled), never a table; every string renders as text; no link into the app. |
| Retention (Saklama) | `Retention` | RET-1 (BIL-1): `retention_until = ended_at + RETENTION_DAYS` 90 on the `Entitlement`. Until then the data stays, the brief and exports still work, and a new subscription reactivates everything. The daily `retention-sweep` archives the companies past the date (`PausedReason` `retention`), sets `purge_due` and removes expired export objects; it deletes nothing else. |
| Purge (Silme) | `Purge` | The one delete path in North (ADR 0016): `purge_owner(user_id, reason)`, service role only, refused before `retention_until`; disables the append-only triggers inside its transaction, deletes the owner's rows, re-enables them, writes an append-only `purge_log` row (hashed user id, counts, reason). The worker first marks the purge (`purge_begin` stamps `entitlements.purge_started_at`; from then on the entitlement stays `ended`, so a resubscribe cannot land mid-purge), removes storage objects and the owner's task workspaces (every row, paged past 1000), then calls the function and `auth.admin.deleteUser`. Off by default (`RETENTION_PURGE_ENABLED`); `scripts/purge-due.ts` runs it on request. The smoke harnesses clean their owners with it. |
| Agent Run | `AgentRun` | One execution of an agent for one task: model, tokens, cost, duration, trace. |
| Model Gateway | `Gateway` (`startGateway`) | The loopback server in the worker that the agent subprocess calls instead of the model API. The subprocess carries only the placeholder key `north-gateway`; the gateway holds the real key, injects it, refuses any request without the placeholder or with a non-loopback Host, and answers 402 once the UTC day's spend has reached `NORTH_DAILY_CAP_USD` (`GatewayBudget`; a cap of 0 is no cap). It prices every 2xx reply from its usage; a model it has no price for is charged the dearest rate and counted as `unpriced`, and a reply with no readable usage closes the day (402 `north_budget_unpriced`) until the next UTC day; a 2xx stream that carried only an `error` event is an upstream error and costs nothing. The worker starts it when `AGENT_RUNTIME=claude-agent-sdk` (`buildRuntimeDeps`, `WorkerDeps.gateway`); the single-call LLM client goes through it too, so every model call of the process is capped. `/health` shows its mode and the day's budget, never the key. |
| Model Profile (Model profili) | `ModelProfile` | TST-1: which models the role aliases resolve to: `production` (Opus-class routing), `staging` (Sonnet) or `smoke` (Haiku), from `NORTH_MODEL_PROFILE` (`WorkerDeps.profile`). Any profile runs in development; under `NODE_ENV=production` anything but `production` needs `NORTH_ENV=staging`. |
| Test Fence (Test çiti) | `FencePolicy` | TST-5: with `NORTH_TEST_FENCE=1` every outside target an action names must be a test account on the fence's lists (`NORTH_FENCE_*`; Vercel projects by prefix, `e2e-` by default; Stripe test keys only), or it is blocked (default deny); a target the worker cannot determine in live mode is blocked too ("unknown target for <kind>"). The gate records a fenced action `blocked` with `test_fence` and a `blocked_reason` naming the target. `WorkerDeps.fence`; refused under `NODE_ENV=production` unless `NORTH_ENV=staging`. |
| Query Embedder (Sorgu gömücü) | `Embedder` | LRN-7: turns a memory search query into a vector through the `embed` Edge Function (`edgeFunctionEmbedder`, 5 s timeout) so `search_memory_hybrid` can rank by meaning; null on any failure, and search then goes by words. On in live mode, in sandbox only with `NORTH_EMBED_QUERIES=1` (`nullEmbedder` otherwise). |
| Cassette | `CassetteRequest` / `CassetteResponse` | One recorded exchange with the model API, stored as `cassettes/<key>.json`; the key is the sha256 of the request path, its `anthropic-beta` flags and its body, after UUIDs, ISO timestamps and `Task id:` lines are normalised. The gateway writes them in `record` mode and serves them in `replay` mode (a miss is a 502 naming the key). The stored request is scrubbed of keys, bearer tokens and `@north.test` addresses; the stored response is verbatim, and a response that holds an `sk-ant-` key is not recorded. |

## Relationships

- A `Company` has one current `Thesis`, up to three active `Goal`s, several `Budget` categories, one `Agent` per role, many `Plan`s.
- A `Plan` has many `Task`s; a `Task` belongs to one `Agent` and may produce many `Action`s and `Artifact`s and exactly one `Evidence` when done.
- A K2 `Action` is blocked until its `DecisionCard` is answered (or its safe default applies at the due time). A K3 `Action` has no default and never runs without an explicit answer.
- Every `Action` and `LedgerEntry` is immutable once written.
- A `Campaign` belongs to one executed `ads.start` `Action` (`action_id` unique) and to the `Task` that proposed it; every later pause or resume is a new `Action` row, the campaign row is only the summary. A `CapCard` belongs to one `Campaign` and one day.
- A `MetricSample` with `channel` scope belongs to a `Campaign` or an `OutreachBatch` through its provenance key; a `company`-scope sample belongs to neither.
- A `LedgerEntry` references its `AttributionWindow` (the provenance with its `windowEnd`), the `Campaign` when its channel is an ads channel, and the `Action` that caused the spend. Its `before` / `after` are the source's cumulative attributed metric.
- An `OutreachBatch` is one `DecisionCard` and many `email.send.first_contact` `Action`s; each action has its own `Lead`, message id and `Evidence`. A `Lead` is contacted by at most one batch, and is in at most one open batch: while a first contact is `pending` (card open, or approved and about to be performed), every address it names (`to` and its batch's recipient list) is held (`held_outreach_addresses`), so the next batch's input (`leadsFreeForOutreach`) skips it, `plan_week` counts only free leads (`leads.count`; at 0 no `outreach_batch` is scheduled) and a first contact's card opens only through `open_first_contact_card`, which checks the holds and writes the card with its pending action in one transaction under the company's lock (`batch_mismatch` when held); a batch whose leads are all held gets none, like a company with no new lead. A first contact without `batchId` is a batch of one: its recipient must be a free `new` lead too. An auto-approved first contact passes the same checks on its own recipient and is recorded under the same lock (`record_auto_first_contact`). Whatever approved it, a first contact claims its lead right before the send with one conditional write only one action can win (`new` → `contacted`, the action in `contact_action_id`); the loser sends nothing, and a failed send releases its claim so the lead is `new` again.
- A `Signal` belongs to one `Company` and one `SignalSource` (unique by `source_ref` within them). A converted `Signal` references its `DecisionCard` (`converted_card_id`, the `signal.pursue` card) and its `Task` (`converted_task_id`: the `signal_research` task when approved, the `FixTask` for an `error` signal). An `opportunity` signal that opened a card owns that `LocalDay`'s ISO week under the `OpportunityCap`.
- A `Brief` is one row per `Company` and `LocalDay`; it references nothing and is recomputed from the ledger, the cards, the plan and the signals of that day. Its push and email are `notifications` rows with `kind: brief`.
- A `PlanRevision` belongs to one `Plan` and names the task type it shrank (or dropped, grew or added) with a reason; a `Plan` has one revision per task type that changed against the previous `Plan`.
- An `Incident` is one `error` `Signal`, one `IncidentReport` `Artifact` and one `FixTask`; the `FixTask` produces a `repo.push` on its fix branch, one `PullRequest`, a verified preview and one `deploy.production` `DecisionCard`, exactly like a `build_site` task.
- A user has exactly one `Entitlement` (a `Trial` first), many `BillingEvent`s (the only writers of it), many `BillingSession`s and many `Credit` entries; the entitlement's `company_limit` bounds the user's non-archived `Company` rows at creation, never at run time. A `Credit` `consume` entry belongs to one `AgentRun`.
- A `Usage` row belongs to one user and one owner-local month; it is recomputed additively from the same runs the credit entries count.
- An `Export` belongs to one user and to one `Company` or all of them; its object lives under the user's path and its signed URL is the owner's. A `PublicPage` belongs to one `Company` and shows nothing the owner did not choose. A `PortfolioBrief` is composed from the owner's `Brief` rows of one `LocalDay` and stored nowhere.
- When an `Entitlement` ends, every `Company` of the owner carries the `KillSwitch` with `PausedReason` `subscription_ended`; `Retention` starts; the `Purge` is the only thing that ever removes the rows, and it logs itself.
